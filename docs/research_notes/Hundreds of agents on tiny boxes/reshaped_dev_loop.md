# Reshaped dev loop: how hundreds of coding agents could make and verify changes at near-zero infrastructure cost (as of 2026-10-16)

Scope note: every price and claim below is dated by the source's own date where available; where a page carries no date the fetch date (2026-10-16) is given. "Shipping" means a product or feature customers can use today; "Proposed/experimental" means a paper, preview, or vendor claim without general availability. Several key primary sources (the CACM 2016 Piper paper, Devin's pricing page, Ona's pricing page, Sapling's engineering-blog clone benchmarks) returned 403/404 or had no numbers; those are flagged in Gaps rather than guessed.

## Key question 1: Checkout-less editing (Piper/CitC, Sapling/EdenFS, VFS for Git/Scalar, git partial clone, GitHub Trees API)

### Takeaway
Google and Meta solved "edit a monorepo without a checkout" a decade ago with virtual filesystems (CitC/FUSE, EdenFS) whose workspaces hold only the files you touched (Google: average workspace under ten files). Nothing equivalent is turnkey for ordinary git repos: VFS for Git is Windows-only legacy, EdenFS is not supported externally, and every shipping hosted coding agent (Claude Code cloud, Codex cloud, Cursor cloud agents) still does a full clone into a VM. The closest shipping primitives for a tool like Manor are git partial clone + sparse checkout, and the GitHub Git Data (Trees) API, which lets an agent commit without any working copy at all.

### Cited Findings
- Google (2016 figures): 86 TB, ~9 million files, ~2 billion LOC, 25,000 developers, 16,000 human changes/day plus 24,000 automated commits/day (bots ~1.5x humans); CitC is a cloud storage backend plus a Linux FUSE filesystem, and "the average local copy is 'less than ten files'" because only modified files live in the workspace — [Wikipedia: Piper (source control system), citing Potvin & Levenberg, CACM 59(7) 2016](https://en.wikipedia.org/wiki/Piper_(source_control_system)); design summary also at [CACM fulltext (403 on fetch)](https://cacmb4.acm.org/magazines/2016/7/204032-why-google-stores-billions-of-lines-of-code-in-a-single-repository/fulltext)
- CitC "layers edits over the repository rather than checking it out"; workspaces are available from any machine and all writes are snapshotted — [search summary of CACM 2016 / arpitbhayani write-up](https://arpitbhayani.me/videos/google-monorepo-managing-billions-of-lines-of-code)
- Meta Sapling (Nov 2022 blog): "In Sapling, cloning the repository downloads almost no history. Instead, as you use the repository we download just the commits, trees, and files you actually need"; the internal repo has "tens of millions of files, tens of millions of commits, and tens of millions of branches"; the virtual file system (EdenFS) makes "clones and checkouts... very fast" but "is not yet publicly available"; "Many of our scale features require using a Sapling-specific server and are therefore unavailable in our initial client release" — [Meta Engineering, Sapling announcement](https://engineering.fb.com/2022/11/15/open-source/sapling-source-control-scalable/)
- Sapling README (fetched 2026-10): EdenFS "only populates working directory files on demand, as they are accessed"; "while it is used in production within Meta it is not yet supported for external usage" — [facebook/sapling README](https://cdn.jsdelivr.net/gh/facebook/sapling@main/README.md)
- Microsoft Windows repo: ~270 GB working directory, >3 million files; full clone would need a ~100 GB packfile taking hours; 2017 GVFS reports: clone up to 12 h, checkout ~3 h -> ~30 s, `git status` ~10 min -> 4–5 s — [I Programmer](https://i-programmer.info/news/177/10803.html); [Gigazine (Feb 2017)](https://www.gigazine.net/gsc_news/en/20170208-microsoft-gvfs-problem); [InfoWorld](https://www.infoworld.com/article/3715261/how-microsoft-scales-git-for-massive-monorepos.html)
- VFS for Git "fetches only refs and the first tree at clone time, with objects fetched on demand"; Scalar is the successor that applies recommended git config plus background maintenance, with features folded into git itself — [GitLab epic on VFS for Git protocol](https://gitlab.com/groups/gitlab-org/-/epics/93); [Microsoft DevBlogs: Introducing Scalar (2020)](https://devblogs.microsoft.com/devops/?p=58465)
- Plain git today: `git clone --filter=blob:none --sparse` then `git sparse-checkout set <dirs>` materialises only the needed directories; partial clone usable since git 2.19, sparse-checkout since 2.25, cone mode default since 2.37; known pitfalls where sparse init fetched everything on 2.25.1 — [stackharbor guide](https://stackharbor.com/en/knowledge-base/git-partial-clone-sparse-checkout-large-repos/); [dev.to partial/sparse clone guide](https://dev.to/cristiansifuentes/git-clone-like-a-pro-from-b-develop-to-partial-sparse-clones-basic-expert-dnc)
- GitHub Git Trees API: `POST /repos/{owner}/{repo}/git/trees` "accepts nested entries", takes a `base_tree` SHA so unlisted files are kept, lets you pass file `content` inline ("GitHub will write this blob out and use that SHA for this entry"), deletes via `sha: null`; to apply you "commit the tree and then update a branch to point to the commit". The 100,000-entry / 7 MB limit applies only to recursive GET — [GitHub REST docs: Git trees](https://docs.github.com/en/rest/git/trees)
- Hosted agents still clone. Claude Code cloud sessions: "each session gets a fresh virtual machine (VM) running Ubuntu 24.04 on x86_64... with your repository cloned"; `claude --cloud` "clones your current directory's GitHub remote at your current branch"; repos without GitHub are bundled and uploaded if "under 100 MB"; a "linked worktree with a sparse checkout... isn't uploaded" — [Claude Code docs: cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web); [Claude Code docs: cloud environments](https://code.claude.com/docs/en/cloud-environments)
- Cursor Cloud Agents "clone your repo from GitHub, GitLab, Azure DevOps Services, or Bitbucket Cloud" into isolated VMs; environments come from agent-led setup, a snapshot, or a Dockerfile — [Cursor docs: Cloud/Background Agents](https://cursor.com/docs/background-agent)
- Codex cloud: "creates a container and checks out the repo at the selected branch or commit SHA"; with a cached container it "clones and checks out the default branch during setup, then checks out the chat's branch when resuming"; "Codex caches container state for up to 12 hours" — [OpenAI Codex docs: cloud environment](https://learn.chatgpt.com/docs/environments/cloud-environment)

### Inferences
- The Google/Meta pattern is "one shared repo image, per-agent overlay of a handful of files". For a git-hosted repo the shipping approximation is: one warm blobless clone per host, plus per-agent `git worktree` with sparse-checkout limited to the task's directories, plus a shared read-only `node_modules` (pnpm store or a bind-mounted install) so the per-agent footprint is tens of MB, not GB.
- A fully checkout-less agent is feasible today via the Trees API: read files with the Contents API, propose edits as a tree against `base_tree`, create a commit, push a ref. Cost is API calls, not RAM. The catch is verification: nothing can run `tsc` or tests against an API-only change, so this only works paired with Key question 2 (a shared verifier that materialises the diff) or Key question 3 (model-side verification).
- Requirements this imposes on a repo/Manor: deterministic install (lockfile; pnpm or Yarn PnP so the dependency store is shareable), a build graph that can compute "affected" from a path list (Nx/Turbo/Bazel-style), no postinstall scripts that write into the tree, and `.gitattributes`/LFS discipline because the Claude Code uploader refuses odd git layouts.

### Gaps
- Could not fetch the CACM 2016 fulltext (403 at both ACM mirrors); the per-workspace "<10 files" figure comes via Wikipedia's citation of it. No published number for CitC latency per file open.
- No Meta-published clone/checkout benchmark for EdenFS; the "tens of millions of files in seconds" claim appears only in an unofficial talk transcript, so it is not cited.
- No vendor (Anthropic, OpenAI, Cursor, Google Jules) discloses using partial or sparse clones; all describe full clones. Jules' and Amp's sandbox designs were not found at all.
- No evidence found of any shipping coding agent operating purely through the GitHub Contents/Trees API without a working copy (Sweep-style approaches were not surfaced by search).

## Key question 2: Verification as a shared service (fleet language server, remote execution, speculative/batched verification)

### Takeaway
The expensive part of per-agent verification is cold start and duplication, not CPU-seconds: Google found over 99% of affected tests never fail and batches changes into "milestones" to amortise testing; Uber's SubmitQueue speculates on queue outcomes and cut land-time 74%; Microsoft's native TypeScript compiler cuts typecheck 10x and halves memory, making a single warm per-repo checker that serves many worktrees realistic. Remote-execution vendors publish core caps, not per-CPU-second prices.

### Cited Findings
- Google TAP (ICSE-SEIP 2017): "A milestone is typically cut every 45 minutes during peak"; milestones can be "as large as 4.2 million tests"; "looking at the overall test history of 5.5 Million affected tests in a given time period, only 63K ever failed; the rest never failed even once"; pass-to-fail ratio per change "is 99:1"; TAP "integrates and tests... more than 13K code projects" per day; compute demand "were growing quadratically" before scheduling changes; "Even with enormous resources dedicated to testing, we are unable to regression test each code change individually" — [Memon et al., Taming Google-Scale Continuous Testing (PDF)](https://web.eecs.umich.edu/~xwangsd/courses/w23/readings/googletest.pdf); abstract at [Google Research pub45861](https://research.google/pubs/pub45861/)
- Uber SubmitQueue (Aug 31, 2023): speculatively builds queued changes in parallel, treats changes touching no shared build targets as independent, and lands out of order when "every path in the speculation tree" agrees; reported "74% improvement in the wait time to land code" — [Uber Engineering: Bypassing Large Diffs in SubmitQueue](https://www.uber.com/en-US/blog/bypassing-large-diffs-in-submitqueue/); [DevOps.com summary](https://devops.com/efficient-ci-at-scale-lessons-from-uber/)
- Native TypeScript (Go port, Microsoft, Mar 2025): `tsc` on VS Code (1.505M LOC) 77.8 s -> 7.5 s (10.4x); Playwright 11.1 s -> 1.1 s; TypeORM 17.5 s -> 1.3 s; "Overall memory usage also appears to be roughly half"; editor project load 9.6 s -> ~1.2 s (8x); ships as TypeScript 7.0 — [Microsoft TypeScript blog: A 10x Faster TypeScript](https://devblogs.microsoft.com/typescript/typescript-native-port/); Dec 2025/Jan 2026 status still "up to 10x faster" — [InfoQ Jan 2026](https://www.infoq.com/news/2026/01/typescript-7-progress)
- BuildBuddy pricing (fetched 2026-10-16): Personal/free "up to 80 Linux cores" remote build and 100 GB cache transfer; Team "up to 800 Linux cores", cache overage shown as "$X / GB" (unpublished); Enterprise unlimited, quote-based; Mac cores "$45 / core"; "BuildBuddy doesn't apply hard limits" on short bursts — [BuildBuddy pricing](https://www.buildbuddy.io/pricing)
- EngFlow: no public per-CPU price; "Contact us for a custom quote"; AWS Marketplace listing is contract-based with fixed entitlements — [EngFlow docs overview](https://docs.engflow.com/overview.html); [AWS Marketplace listing](https://aws.amazon.com/marketplace/pp/prodview-nklfrw6pel6vw)
- Nx Cloud (third-party guide dated June 2026, unverified against nx.dev): free tier 500 CI pipeline hours/month, Pro $300/month; Nx supports distributed task execution across agents, which Turborepo does not — [cicdpipelinecost.com monorepo strategies](https://cicdpipelinecost.com/monorepo-strategies); [nx.dev: Turbo and Nx](https://19.nx.dev/concepts/turbo-and-nx)
- Anthropic code execution tool (API, fetched 2026-10-16): "Code execution is free when used with web search or web fetch"; otherwise "Additional usage beyond 1,550 hours is billed at $0.05 USD per hour, per container" — [Claude Platform pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- GitHub Actions (the compute behind Copilot coding agent): Linux 2-core $0.006/min x64, $0.005/min arm64; 2,000 free minutes (Free), 3,000 (Pro/Team), 50,000 (Enterprise Cloud) — [GitHub docs: billing for Actions](https://docs.github.com/en/billing/managing-billing-for-your-products/managing-billing-for-github-actions/about-billing-for-github-actions)
- Tool "reviewgate" (PyPI, 2026): hybrid where an LLM proposes edge-case tests but "No model is involved in the pass or fail decision"; has a "worktree mode" for agents mid-session — [reviewgate on PyPI](https://pypi.org/project/reviewgate/0.5.0/) (vendor README, not an evaluation)

### Inferences
- TAP's 99:1 pass ratio and "63K of 5.5M ever failed" is the strongest argument for lazy verification: run the full suite rarely, on batched milestones; per-agent, run only the targets the diff affects, and accept that most agent diffs will never trip a test. This is what GitHub merge queue / Uber speculation already do at merge time; the proposal is to move the same speculation earlier, to the agent's draft.
- A single warm `tsgo --watch`/language-server process per repo (not per agent) is the fleet-scale analogue of CitC's shared backend: with a 10x faster, half-memory checker, one daemon can re-check an agent's worktree in roughly a second for mid-size repos. Agents would call a local socket ("check these N files against worktree W") instead of spawning `tsc` each turn. This is proposed, not shipping as a product, but every component (tsgo, LSP, git worktrees) ships.
- Remote execution economics: because BuildBuddy and EngFlow price by core caps/contract, a Manor-scale user can't buy "CPU-seconds"; the cheap shared verifier is a self-hosted daemon, not RBE. RBE pays off only with Bazel/Buck2 hermetic targets.
- Requirements on a repo: hermetic, path-addressable tasks (so "affected" is computable); tests that are deterministic enough to run in batch (flakes poison speculation, as the TAP paper notes); a project-references/tsconfig layout so incremental checking is per-package.

### Gaps
- No published per-CPU-second price from any Bazel RBE vendor (BuildBuddy Linux, EngFlow); Google Cloud RBE is not on offer. Cost comparisons must use generic sandbox vCPU-hour rates from Key question 7.
- No public product implements "one typecheck daemon serving many agent worktrees"; this remains an inference from tsgo/LSP capabilities.
- The TAP paper's dataset is Feb–Mar 2016; no newer Google numbers found.

## Key question 3: Model-side verification (does running tests change the outcome? LLM-as-judge, hybrid verifiers)

### Takeaway
The best available evidence says execution feedback buys accuracy on the hardest tasks at the cost of roughly 2x turns and tokens: execution-free trajectories have 40% fewer tokens and 10–30 turns versus 20–60 for execution-backed ones, and the gap shows up at the top of the difficulty curve. Execution-free (LLM-judge) and execution-based verifiers each plateau around 43% Best@K on SWE-bench Verified but combine to 51%, so the cheapest reliable design is a hybrid: a model pre-screens, execution confirms only when needed.

### Cited Findings
- SWE-ZERO/SWE-HERO (arXiv 2604.01496, 2026): "these execution-free trajectories contain 40% fewer tokens than their execution-backed counterparts"; execution-backed trajectories are "concentrated between 20 and 60 interaction turns; conversely, SWE-ZERO trajectories... typically spanning 10 to 30 turns"; "SWE-HERO achieves superior success rates on the most challenging tasks by trading temporal efficiency for a significant gain in resolution accuracy"; SWE-HERO 7B/14B/32B reach 52.7%/60.8%/62.2% on SWE-bench Verified; the execution-free SWE-ZERO-14B scaling curve goes from 42.1% to 49.1% as training data grows 4k -> 150k PRs; skipping the execution-free pre-stage drops the 32B model from 62.2% to 55.7% — [arXiv 2604.01496 PDF](https://arxiv.org/pdf/2604.01496); [abstract](https://arxiv.org/abs/2604.01496)
- Restricting Claude Code and Codex CLI to a single `execute_code` tool (arXiv 2607.10569, 2026): "Pass rates were statistically tied within each cell"; the restricted agent was "cheaper than -- or statistically tied with" its tool-rich rival in 3 of 4 cells; the exception (SWE-bench/Claude) was +14.4% costlier, "not significant", attributed to "failure-cost on doomed-run trajectories" — [arXiv 2607.10569](https://arxiv.org/abs/2607.10569)
- R2E-Gym (arXiv 2504.07164, NeurIPS 2025): execution-based verifiers "cannot differentiate between patches with identical test pass-rates"; execution-free verifiers "are biased and often rely on stylistic features"; Best@K "quickly plateaus for both methods, converging similarly to 43.7% and 42.8%"; hybrid reaches "51% on the SWE-Bench Verified benchmark" (secondary summary: Pass@1 34.4%, Best@16 hybrid 49.4%, Best@26 hybrid 51.0%) — [arXiv 2504.07164](https://arxiv.org/pdf/2504.07164); [NeurIPS 2025 page](https://neurips.cc/virtual/2025/131676)
- Agentless (2024): "achieve both the highest performance (32.00%, 96 correct fixes) and low cost ($0.70) on SWE-bench Lite"; an earlier config reported "$0.34 per issue"; selection filters "patches with syntax errors or that fail repository tests before re-ranking" and majority-votes — [arXiv 2407.01489](https://arxiv.org/html/2407.01489v2); [GitHub mirror README](https://gitblind.noratr.app/mrvoh/Agentless)
- CodeMonkeys (Stanford, 2025): 57.4% on SWE-bench Verified with Claude 3.5 Sonnet; "running CodeMonkeys on SWE-bench Verified cost $2300 USD" (500 tasks, so ~$4.60/task); its selection method lifts an ensemble of top submissions to 66.2% — [Stanford Scaling Intelligence blog](https://scalingintelligence.stanford.edu/blogs/codemonkeys)
- AgentForge ablation on SWE-bench Lite: removing any agent reduces performance, with "the Tester and Debugger together contributing the largest gains" — [arXiv 2604.13120](https://arxiv.org/pdf/2604.13120)
- Secondary accounts of Anthropic's harness experiment (planner/generator/evaluator): without a harness ~$9 over 20 min and a non-working result; with the three-agent harness ~$200 over 6 hours and a working game; "tuning a standalone evaluator to be skeptical was much more tractable than trying to make the generator judge itself honestly"; the evaluator was given Playwright MCP — [Addy Osmani, Agent Harness Engineering](https://addyosmani.com/blog/agent-harness-engineering/); [noze.it summary](https://www.noze.it/en/insights/harness-engineering/) (secondary; original Anthropic post not retrieved)

### Inferences
- "Where does running tests pay for itself?" From SWE-ZERO/HERO: execution roughly doubles turns (and therefore token spend) and the accuracy gain concentrates in the hard tail. For a fleet, the token-optimal policy is to skip execution on tasks the model is confident about and spend execution only where a cheap judge is unsure; R2E-Gym's plateau-then-combine result supports a two-stage gate (judge first, execute on disagreement/low confidence).
- Compute is not the binding constraint in any of these papers; tokens are. Agentless at $0.34–0.70/issue and CodeMonkeys at ~$4.60/task are almost entirely LLM cost. Dropping execution saves the ~2x token overhead more than it saves sandbox dollars.
- Requirements on a repo/Manor: fast, narrowly scoped tests the judge can name ("run only `auth.spec.ts`"), machine-readable lint/typecheck output the judge can be trained/prompted on, and a confidence signal from the agent (e.g., self-reported risk) to route between judge-only and execute.

### Gaps
- No ablation found that takes a *frontier* agent (Claude Code, Codex) and removes test execution at inference time while holding everything else fixed; the 40%-fewer-tokens figure is for distilled Qwen trajectories, and the SWE-ZERO 49.1% vs SWE-HERO 60.8% comparison at 14B is between differently trained models, not a pure inference-time ablation.
- No "predict the lint result" paper surfaced; no published accuracy for an LLM predicting `tsc`/ESLint output without running it.
- The Anthropic harness experiment figures ($9 vs $200) are from secondary blogs; the primary Anthropic post was not retrieved.

## Key question 4: Cost accounting (tokens vs compute; where "near zero" would come from)

### Takeaway
For a Claude Code-style task, sandbox compute is a rounding error against tokens: Anthropic's own worked example prices a one-hour Opus coding session at ~$0.71, of which the $0.08 runtime fee is ~11%, and a 2 vCPU/4 GiB sandbox on E2B/Daytona costs ~$0.17/hour wall-clock. Token levers (cache reads at 0.025–0.1x, Haiku 5.5 at $0.10/$0.50, Batch API at 50%) move the bill 2–50x; compute levers move it by pennies.

### Cited Findings
- Anthropic API prices (fetched 2026-10-16): Opus 4.8/4.7/4.6/4.5 $5 in / $25 out per MTok, cache read $0.50; Sonnet 5.5 $2/$10 (cache read $0.10); Sonnet 4.6/4.5 $3/$15; Haiku 5.5 $0.10/$0.50 for prompts ≤100K tokens ($0.50/$2.50 above); Haiku 4.5 $1/$5; Fable 5.1 and Mythos 5.1 $10/$50 with cache reads at $0.25 (0.025x); cache read generally "0.1x base input price (0.025x on Claude Fable 5.1 and Claude Mythos 5.1; 0.05x on Claude Opus 5.5 and Claude Sonnet 5.5)"; Batch API "50% discount on both input and output tokens"; Claude 4.7+ tokenizer "produces approximately 30% more tokens for the same text"; 1M context at standard pricing on 4.6+ — [Claude Platform pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Managed Agents runtime: "$0.08 per session-hour", metered on running status; "Time spent idle (waiting for your next message or a tool confirmation), rescheduling, or terminated does not count toward runtime"; "Overlapping activity from concurrent threads is counted once"; no batch mode; web search $10/1,000 — [Claude Platform pricing](https://platform.claude.com/docs/en/about-claude/pricing); [Claude Managed Agents blog](https://claude.com/blog/claude-managed-agents); launched public beta 2026-04-08 per [Finout](https://www.finout.io/blog/anthropic-just-launched-managed-agents.-lets-talk-about-how-were-going-to-pay-for-this)
- Anthropic worked example (as relayed): one-hour coding session, 50K input + 15K output on Opus ≈ $0.705 total, of which runtime is $0.08 — [Finout](https://www.finout.io/blog/anthropic-just-launched-managed-agents.-lets-talk-about-how-were-going-to-pay-for-this); [TrueFoundry](https://www.truefoundry.com/blog/claude-managed-agents-pricing) (model named differently across the two)
- Claude Code cloud sessions: "It counts toward your plan's usage limits alongside the rest of your Claude and Claude Code usage, and there's no separate charge for the cloud VM" — [Claude Code docs](https://code.claude.com/docs/en/claude-code-on-the-web)
- Cursor Cloud Agents: "charged at API pricing for the selected model"; docs say nothing about separate compute billing — [Cursor docs](https://cursor.com/docs/background-agent)
- Devin (third-party, conflicting): Core $20/mo + $2.25/ACU; Team $500/mo with 250 ACUs at $2/ACU; "1 ACU is roughly 15 minutes of work"; typical bug fix 2–3 ACU ($4.50–6.75); one source reports a 2026 shift to Pro $20/Max $200 seat quotas — [pricepertoken.com](https://pricepertoken.com/coding-assistants/devin); [usagebar.com](https://usagebar.com/blog/devin-pricing-and-rate-limits); official devin.ai/pricing returned 404
- Per-task SWE-bench cost estimates (third-party): Opus 4.5 ~$0.68 per resolved task vs DeepSeek V3.2 $0.028 — [ssojet.com](https://ssojet.com/blog/cheapest-ai-coding-models); HAL lists total run cost for SWE-bench Verified Mini, e.g. Claude Opus 4 $1,330.90 at 50% — [HAL leaderboard](https://hal.cs.princeton.edu/swebench_verified_mini)
- Google Jules: no compute billing; caps of 15 tasks/day (3 concurrent) free, 100/day (15 concurrent) in Pro, 300/day (60 concurrent) in Ultra — [Jules docs: usage limits](https://jules.google/docs/usage-limits/)
- GitHub Copilot coding agent: "Each coding agent session consumes one premium request"; Actions minutes "come from your account's monthly allowance of free minutes for GitHub-hosted runners" — [GitHub docs: Copilot billing](https://docs.github.com/en/enterprise-cloud@latest/billing/managing-billing-for-github-copilot/about-billing-for-github-copilot)
- Codex Cloud is "available to eligible Plus, all Pro tiers, Business, Enterprise... not included with Free or Go"; usage limits vary by plan; business "Codex credit plans" exist — [OpenAI Help: Codex in ChatGPT](https://help.openai.com/en/articles/11369540-codex-in-chatgpt)

### Inferences
- Arithmetic for a one-hour agent task on a 2 vCPU / 4 GiB sandbox (rates from Key question 7): E2B/Daytona wall-clock = 2×$0.0504 + 4×$0.0162 ≈ $0.17; Modal Sandbox (1 physical core) ≈ $0.14 + 4×$0.024 ≈ $0.24; Cloudflare standard-3 with CPU active 5% ≈ $0.007 CPU + $0.072 memory + $0.004 disk ≈ $0.08; Vercel 5% active ≈ $0.013 + $0.085 memory ≈ $0.10; Fly Sprites paused between tool calls ≈ $0.01–0.02. Against this, a realistic Claude Code hour is far above the $0.63 token figure in Anthropic's toy example: 100 turns × 100K cached context at Opus 4.8's $0.50/MTok cache-read rate alone is ~$5 before output tokens. Compute is therefore ~1–15% of task cost, and under 3% once sessions use cached long contexts.
- "Next to zero" compute is already available on three shipping surfaces at $0 marginal: Claude Code cloud sessions (plan usage, "no separate charge for the cloud VM"), Jules (task caps), Codex cloud (plan-included). Vendors absorb sandbox cost because it is immaterial next to inference.
- The real cost levers for a 100-agent fleet are token-side: route to Haiku 5.5 ($0.10/$0.50) for screening and Sonnet 5.5 ($2/$10) for edits (10–50x cheaper than Opus/Fable); keep per-repo system context stable so cache reads hit at 0.025–0.1x; fewer turns via execution-free drafting (Key question 3's 40% token saving); Batch API 50% for non-interactive passes (not available for Managed Agents). Note the 4.7+ tokenizer's ~30% token inflation partly offsets price cuts.
- Where compute does matter: wall-clock-billed sandboxes left running while the model thinks (idle 95%), and memory-dominated bills on active-CPU platforms (Vercel/Cloudflare bill provisioned memory the whole time). Pause-on-idle (Sprites, E2B pause, Claude Code's "VM pauses with its files saved") is the fix.

### Gaps
- No official per-task cost from Anthropic or OpenAI for a Claude Code/Codex SWE-bench run; all per-task dollar figures are third-party estimates.
- Devin and Ona official pricing pages could not be fetched (404 / no prices on page); their numbers are secondary and conflicting.
- Whether Cursor bills compute separately is not stated in its docs.
- The HAL "Mini" subset size (assumed 50 tasks) was not confirmed on the page, so the ~$26/task implied by $1,330.90 is unverified.

## Key question 5: Borrowed compute (developer's own hardware, browser runtimes, spot instances, snapshots)

### Takeaway
Shifting compute to hardware the user already pays for is the only path to literally zero marginal sandbox cost, and it ships today in two forms: Claude Code Remote Control (the session runs on your laptop, the phone is a window) and StackBlitz WebContainers (Node in the browser tab; "No paying by the minute for cloud VMs", the basis of bolt.new's margins). Spot instances (up to 90% off) and Firecracker snapshot/restore (state in <5 ms, memory faults dominate) are the cloud-side analogues.

### Cited Findings
- Claude Code Remote Control: `/remote-control` or `claude remote-control` makes a session already running on your machine reachable from phone/browser; "Files, MCP servers, and tools never leave your machine, and only the chat interface flows through Anthropic's cloud"; since Aug 2026 phones can also start new sessions on registered machines — [noqta.tn (Feb 2026)](https://noqta.tn/en/news/anthropic-claude-code-remote-control-mobile-2026); [pasqualepillitteri.it (Aug 2026)](https://pasqualepillitteri.it/en/news/12249/claude-code-start-session-from-phone); official pointer in [Claude Code cloud docs](https://code.claude.com/docs/en/claude-code-on-the-web) ("Remote Control lets you reach them from your phone or browser")
- Anthropic cloud docs explicitly route heavy workloads to owned hardware: VM is "4 vCPUs, 16 GB of RAM... For workloads beyond these limits, use Remote Control to run Claude Code on your own hardware, or run cloud sessions in a self-hosted environment" — [Claude Code docs: cloud environments](https://code.claude.com/docs/en/cloud-environments)
- Coder offers self-hosted execution for Claude Code cloud sessions: "Execution environments provisioned and torn down automatically" on customer infrastructure, with Anthropic keeping orchestration and inference — [coder.com/anthropic](https://coder.com/anthropic)
- WebContainers: "browser-based runtime for executing Node.js applications", "spinning up the entire dev environment in milliseconds", "Compute is done locally. No paying by the minute for cloud VMs", "Scales to millions" via CDN caching; "Always free for Open Source", commercial licence via separate page — [webcontainers.io introduction](https://webcontainers.io/guides/introduction)
- bolt.new on WebContainers: competitors "start a fresh cloud container per session, adding cold starts and per-user costs, while WebContainer runs the app in the browser"; StackBlitz's "marginal cost is AI tokens rather than hosting"; company-sourced claim of gross margins near 70%; limitation: cannot run native binaries not compiled to WASM (no Docker-in-Docker, no native Postgres) — [PostHog newsletter](https://newsletter.posthog.com/p/from-0-to-40m-arr-inside-the-tech); [Sacra](https://sacra.com/chat/h/5927dd21-2981-402b-869b-0780aed2a1f0); [toolfreebie](https://toolfreebie.com/?p=231)
- AWS Spot: "available at up to a 90% discount compared to On-Demand prices", for "stateless, fault-tolerant, or flexible applications" — [AWS EC2 Spot](https://aws.amazon.com/ec2/spot/)
- Firecracker: resume "a fully-initialized microVM in under 5ms" (state file only); memory is mapped lazily so page faults dominate; REAP (ASPLOS 2021) cut hello-world from 182 ms to 15 ms; "each microVM has an overhead of less than 5MB of memory" (vendor claim) — [Blaxel: snapshot/hibernate](https://blaxel.ai/blog/sandbox-snapshot-hibernate-resume-ai-agents); [mohakchugh blog](https://mohakchugh.is-a.dev/blog/firecracker-microvm-snapshot-restore-serverless-cold-start)
- Vercel Sandbox runs "each sandbox as an isolated container inside a Firecracker microVM"; filesystem snapshot restores went from p75 >40 s to under one second via parallelisation and local caching — [Vercel blog: optimizing sandbox snapshots](https://vercel.com/blog/optimizing-vercel-sandbox-snapshots)
- Claude Code cloud idle behaviour (free pause/resume on Anthropic's side): "after a few minutes without activity, a session's VM pauses with its files saved. Your next message restores the same VM"; a reclaimed VM is rebuilt from an environment cache that is "a filesystem snapshot" refreshed "after roughly seven days"; setup scripts over "roughly five minutes" aren't cached — [Claude Code docs: cloud environments](https://code.claude.com/docs/en/cloud-environments)

### Inferences
- For Manor (an Electron desktop app already on the developer's machine) the "borrowed compute" model is the default: the marginal cost of N agents is RAM on the laptop, and the ceiling is memory, not dollars. The 1–4 GB/agent problem is therefore a *density* problem solved by sharing (one checkout image, one dependency store, one typecheck daemon per repo) rather than a billing problem. Remote Control is the proof that Anthropic sees the laptop as a legitimate execution host.
- WebContainers show the extreme: zero server compute by moving Node into the client. For a Manor-like tool this suggests an experimental mode where lint/typecheck/vitest run in a WebContainer or Node worker inside the app's own renderer/utility process, sharing a single V8 heap for many lightweight agents, with native-binary tasks escalated to a real shell.
- Spot plus snapshot/restore makes "preemptible agent sandboxes" viable: with sub-5 ms state restore and cheap filesystem snapshots, an agent can be checkpointed between tool calls and resumed on any node. No vendor sells this combination as a product yet.
- Requirements: tasks that tolerate interruption (idempotent steps, state in git not in process memory), no native dependencies for the browser-runtime path, and an explicit memory budget per agent.

### Gaps
- No published Remote Control architecture doc from Anthropic beyond marketing summaries; no measurement of its bandwidth or latency.
- WebContainers commercial pricing page not retrieved; bolt.new margin figure is company-sourced.
- No benchmark combining Firecracker restore latency with sandboxes-per-host for agent workloads; no vendor discloses sandbox density.
- No evidence of any shipping agent product using spot/preemptible capacity with checkpointing.

## Key question 6: Fleet orchestration in the wild (Claude Code cloud/Managed Agents, Codex cloud, Devin, Factory, Cursor, Jules, Amp, Ona)

### Takeaway
Every hosted agent provisions one VM/container per task with a full clone, caches a post-setup filesystem snapshot to skip reinstalls, pauses on idle, and folds compute into the subscription or token bill; none avoid a full checkout and none publish densities or per-task compute cost. Disclosed specs: Claude Code 4 vCPU/16 GB Ubuntu 24.04 with ~7-day environment cache; Codex 12-hour container cache with no agent-phase network by default; Jules caps by tasks/day; Copilot runs on Actions minutes.

### Cited Findings
- Claude Code cloud (docs, fetched 2026-10-16): "each session gets a fresh virtual machine (VM) running Ubuntu 24.04 on x86_64", "4 vCPUs, 16 GB of RAM"; "The VM may stop tasks that need significantly more memory"; Default environment has "Trusted network access"; setup script snapshot "reuses that snapshot as the starting point for later sessions", rebuilt "after roughly seven days"; idle VM pauses after "a few minutes"; Bash default timeout 2 min (up to 10), backgrounded commands run up to 30 more minutes; "no separate charge for the cloud VM"; GA for Pro/Max/Team — [cloud environments](https://code.claude.com/docs/en/cloud-environments); [cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web)
- Claude Code cloud security: "sensitive credentials (such as git credentials or signing keys) are never inside the sandbox"; a proxy "verifies this credential and the contents of the git interaction" (e.g. only pushes to the configured branch) before adding the real token — [Anthropic: Beyond permission prompts](https://claude.com/it/blog/beyond-permission-prompts-making-claude-code-more-secure-and-autonomous)
- Sandbox lifetime (support docs via search): "After a few minutes idle, the virtual machine is stopped and its disk is saved as an encrypted snapshot. The sandbox environment expires 30 days after it was created" — [Claude Cowork architecture overview](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview)
- Managed Agents: $0.08/session-hour runtime covers "the sandboxed execution environment, state management, checkpointing, and error recovery"; multi-agent coordination and self-evaluation gated behind a research preview — [Finout](https://www.finout.io/blog/anthropic-just-launched-managed-agents.-lets-talk-about-how-were-going-to-pay-for-this); [Claude Platform pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- OpenAI Codex cloud: default image "universal" (public as `ghcr.io/openai/codex-universal`); setup scripts have internet, agent phase "off by default"; "Codex caches container state for up to 12 hours"; optional maintenance script on resume; Business/Enterprise cache "shared by everyone with access to the environment" — [OpenAI Codex docs](https://learn.chatgpt.com/docs/environments/cloud-environment); image detail from [codex.danielvaughan.com (May 2026)](https://codex.danielvaughan.com/2026/05/31/codex-cloud-environments-setup-scripts-caching-secrets-codex-universal/)
- Cursor Cloud Agents: "Cursor manages VM provisioning, isolation, snapshots, startup, artifacts, and capacity"; "Builds prepare each environment in the background so agents start with repositories and dependencies ready"; paid plan required; billed "at API pricing for the selected model" — [Cursor docs](https://cursor.com/docs/background-agent)
- Google Jules: 15/100/300 tasks per rolling 24 h with 3/15/60 concurrent for Free/Pro/Ultra; no compute line item — [Jules usage limits](https://jules.google/docs/usage-limits/)
- GitHub Copilot coding agent: one premium request per session, dedicated SKU; compute from Actions minutes ($0.006/min Linux 2-core) — [GitHub Copilot billing](https://docs.github.com/en/enterprise-cloud@latest/billing/managing-billing-for-github-copilot/about-billing-for-github-copilot); [Actions billing](https://docs.github.com/en/billing/managing-billing-for-your-products/managing-billing-for-github-actions/about-billing-for-github-actions)
- Ona (ex-Gitpod): "Every agent runs in an isolated VM"; Factory "runs on Factory's cloud infrastructure, with a self-hosted option"; Ona pricing in OCU credits with free tier 4 vCPU/16 GB, 3 parallel environments, auto-delete after 3 days idle; Core from $20/mo — [ona.com/compare/factory](https://ona.com/compare/factory); [morphllm Gitpod alternatives (2026)](https://www.morphllm.com/comparisons/gitpod-alternative)
- Devin: ACU model (~15 min per ACU, $2–2.25) bundles compute and model — [pricepertoken.com](https://pricepertoken.com/coding-assistants/devin)

### Inferences
- The industry-standard pattern is now: (1) clone into a per-task microVM, (2) run a setup script once and snapshot the filesystem, (3) start every later task from the snapshot, (4) pause on idle and reclaim after a window, (5) keep secrets outside the VM behind a proxy. Manor can replicate 2–4 locally with a per-repo "golden worktree + node_modules" image and copy-on-write (APFS clonefile, overlayfs) per agent, which is the cheapest way to get 100 agents from one install.
- Nobody bills sandbox compute separately to end users (Anthropic Managed Agents' $0.08/hour is the only explicit line, and it is ~10% of even a light session). This is strong evidence that providers view compute as negligible and compete on tokens/limits.
- Anthropic's choice of 4 vCPU/16 GB per session, with a note that heavier builds should move to Remote Control, is the only disclosed sizing; it implies ~4 sessions per 64 GB host at most if not oversubscribed, which is why idle pause/reclaim exists.

### Gaps
- No vendor discloses sandboxes per host, VM boot time for a task, or per-task compute cost.
- Sourcegraph Amp and Factory sandbox/billing details were not found.
- Devin and Ona official pricing pages unavailable; figures are secondary and inconsistent.
- No shipping product avoids a full clone; "partial clone" is absent from all docs reviewed.

## Key question 7: Serverless-shaped sandboxes (Modal, E2B, Daytona, Vercel Sandbox, Cloudflare Sandbox SDK, Fly Sprites): prices, cold starts, pause/resume, idle-95% math

### Takeaway
Published rates cluster at $0.05–0.13 per vCPU-hour and $0.009–0.024 per GiB-hour, with cold starts from ~25 ms to 2–3 s. The billing model matters more than the rate: wall-clock providers (E2B, Daytona, Modal) charge ~$0.17/hour for a 2 vCPU/4 GiB box whether or not it is busy, active-CPU providers (Vercel, Cloudflare) still bill provisioned memory for the whole lifetime, and only pause-on-idle (Fly Sprites, E2B pause, Vercel/Daytona stop) gets an agent that is idle 95% of the time down to a cent or two per hour.

### Inferences
- "Idle 95%" worked example, one agent-hour, 2 vCPU/4 GiB, CPU busy 3 minutes: E2B/Daytona wall-clock $0.166 (or ~$0.01 if the orchestrator pauses between tool calls, since pause stops billing); Modal Sandbox $0.238 (min 60 s keep-alive makes aggressive scale-to-zero costly); Cloudflare standard-3 $0.083 (memory-dominated: $0.072 of it); Vercel $0.098 (memory $0.085 of it); Sprites ~$0.01–0.02 (CPU $0.004 + memory $0.004 + storage). At 100 agents that is $1–2/hour (Sprites, paused E2B) vs $8–24/hour (always-on). Over a 160-hour work month the spread is roughly $200 vs $1,500–4,000, still small next to token spend for 100 agents.
- The design implication is "sandbox as a tool call, not a session": start (≤150 ms on E2B/Daytona), run the check, pause. This requires the agent harness to tolerate restores (filesystem persisted, processes not), which Claude Code's own cloud already enforces ("The cache stores files only, not running processes").
- Memory is the irreducible cost on every platform; the way to make it near zero is to not hold 4 GiB per agent: share the dependency store and typecheck daemon on one bigger box (Key question 2) and give each agent a thin overlay (Key question 1).
- Requirements on a repo: cold-start-friendly (setup under Claude Code's ~5-minute cache window; prebuilt snapshot), tests runnable headless in ≤ the sandbox session cap (1 h on E2B Hobby, 45 min on Vercel Hobby), and no long-lived background services needed for verification.

### Gaps
- Cloud sold cold-start numbers come from one undated-methodology blog; no vendor publishes p50/p99 boot latency.
- No vendor publishes sandboxes-per-host or oversubscription ratios, so "density" cannot be computed from public data.
- Modal memory-snapshot availability and speed are disputed across sources; the official pricing page is silent.
- Daytona snapshot pricing not published; Cloudflare Sandbox SDK adds Workers/Durable Objects charges that were not quantified here.
