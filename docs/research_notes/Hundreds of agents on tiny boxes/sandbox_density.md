# Sandbox density: OS and infrastructure techniques for hundreds of mostly-idle dev sandboxes per small machine (as of 2026-10-16)

Scope note: workload is x86-64 Linux; each sandbox = a git checkout + an occasional coding-agent (Node) process that is idle 90%+ of the time (0.01–0.08 cores, 220–500 MB RSS) with rare bursts to several GB / many cores. Baseline today: one k3s pod per project, 1 GiB request / 4 GiB limit, ~8–12 pods on a 48 GB VPS. Every figure below is tagged (measured) when it comes from a benchmark/paper/docs with method, (vendor) when it is a vendor doc or product page, or (marketing) when it is an unqualified headline number.

## Key question 1: Firecracker microVMs — overhead, snapshot/restore, ballooning, and how vendors (Fly Sprites, Lambda, E2B, Modal, Daytona, Northflank, Blaxel, Vercel, CodeSandbox) reach density

### Takeaway
Firecracker's measured VMM overhead is ~3 MB per microVM (AWS, NSDI 2020) and the dominant density techniques every vendor uses are the same four: boot from a pre-warmed memory snapshot instead of a kernel boot; lazily page the snapshot in via `userfaultfd`/`MAP_PRIVATE` so many VMs share the same read-only pages; copy-on-write root filesystems over a shared image; and aggressive pause-to-disk of idle VMs (seconds to minutes of idle) so idle sandboxes consume zero RAM. No vendor publishes a "sandboxes per host" number; per-second prices are now near-identical across E2B/Daytona ($0.000014/vCPU-s, $0.0000045/GiB-s) with Fly Sprites and Vercel billing only active CPU.

### Cited Findings

**Firecracker fundamentals (measured, AWS NSDI 2020 paper)**
- Design claims: "memory overhead of less than 5MB per container, boots to application code in less than 125ms, and allows creation of up to 150 MicroVMs per second per host." — [Agache et al., NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Measured (Figure 7, m5d.metal, pmap non-shared segments): "Firecracker has the smallest overhead (around 3MB) of all VMM sizes measured. Cloud Hypervisor's overhead is around 13MB per VM. QEMU has the [largest]." Overhead is constant regardless of configured VM size. — [NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Lambda density target: "up to 8000 functions on a server to fill the RAM (or more due to soft allocation)… initially targeted 10% on RAM and CPU. For a 1024MB function, this means 102MB of memory overhead." — [NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Soft allocation / overcommit is explicit design: resources "are both soft-allocated and oversubscribed, so can be sold to other slots while one is [idle]… Oversubscription is fundamentally a statistical bet." Each Lambda slot lives at most 12 hours before recycling. — [NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Parallel boot of 1000 microVMs, 50 concurrently: pre-configured Firecracker p99 boot 146 ms vs Cloud Hypervisor 158 ms; a static network interface adds ~20 ms; the minimal guest kernel is 4.0 MB compressed with no modules. — [NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Firecracker block I/O was limited to ~13,000 IOPS (52 MB/s at 4 kB) vs 340,000 native in 2020; network ~15 Gb/s vs 44 Gb/s host — relevant for `npm install` bursts inside microVMs. — [NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)

**Firecracker snapshot/restore mechanics (vendor docs)**
- A snapshot = guest memory file + microVM state file (+ user-managed disks). Restored VMs map the memory file `MAP_PRIVATE`, pages load on demand, writes go to anonymous CoW memory; "This allows memory pages and read-only disks to be shared among multiple microVMs." The memory file must remain unmodified for the restored VM's lifetime. — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- Two memory backends: `File` (kernel page faults) or `Uffd` (userspace fault handler over a Unix socket); `2M` huge pages require Uffd. Diff snapshots (dirtied pages only, sparse file) are developer preview and must be rebased onto a base with `snapshot-editor`. Dirty-page tracking "has runtime cost and negates most huge page benefits." — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- No official restore latency published; docs say resume is optimized for speed, snapshot creation faults in all guest memory, and warn of "high restore latency with cgroups v1" (use cgroup v2). Snapshots must resume on identical hw/sw (e.g. m5n.metal snapshot not restorable on m6i.metal); network connection state not guaranteed after resume; vsock connections close. — [Firecracker snapshot-support.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)
- Third-party measured restore times: 28 ms snapshot restore vs ~1.1 s cold boot — [dev.to/adwitiya](https://dev.to/adwitiya/how-i-built-sandboxes-that-boot-in-28ms-using-firecracker-snapshots-i0k); restore step ~49 ms inside a 179 ms p50 end-to-end — [PandaStack](https://www.pandastack.ai/blog/microvm-malware-detonation-sandbox/). Both single-deployment blog measurements.

**Firecracker balloon / free-page reporting (vendor docs)**
- Balloon is a host-controlled virtio device; the guest must cooperate ("hosts should be ready for Firecracker to use all of its boot memory"); Linux guests inflate at most 1 MiB at a time; if the target is unreachable the balloon retries every 0.2 s and is CPU-intensive. — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)
- Free page reporting: guest reports unused ranges, Firecracker discards them "to reduce host RSS"; starts ~2 s after boot; needs `PAGE_REPORTING` in the guest kernel; with hugetlbfs keep order ≥9 (2 MiB). Free page hinting is developer preview: ~200 ms for a 1 GB VM, has a known race (mitigation: UFFD WRITEPROTECT). — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)
- Traditional balloon inflation frees no memory with 2M hugetlbfs and can increase host usage; `deflate_on_oom` is "not meant for continuous memory reclaim." — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)

Stopped/suspended Machines are not billed CPU/RAM; rootfs costs $0.15/GB per 30 days. ### Inferences
- The vendor playbook for density is: zero RAM for idle (pause/hibernate to object storage within seconds-minutes of idle), shared read-only pages for the warm set (snapshot `MAP_PRIVATE`/uffd), and shared rootfs (CoW overlay). A self-hosted Firecracker setup on a 48 GB box could in principle hold hundreds of *paused* sandboxes (disk-bound, not RAM-bound) with a few dozen *running* ones, since VMM overhead is ~3–5 MB and guest kernel + Node idle RSS (~220–500 MB measured in your workload) becomes the real per-VM cost.
- Per-GiB-hour memory prices cluster at $0.009 (Cloudflare) – $0.016 (E2B/Daytona, derived from $0.0000045/s) – $0.021 (Sprites/Vercel); the differentiator is whether idle time is billed. Sprites' floor for an *awake* but idle Sprite is 0.0625 CPU + 256 MB ≈ $0.008/hour (derived), and warm/cold Sprites cost only storage.
- Fly's measured Claude Code profile (1.5 GB resident avg, bursts to 8 GB) is 3–7x heavier than the 220–500 MB RSS cited in the brief; your 1 GiB request is plausible for an agent-only pod but a 4 GiB limit undershoots Fly's observed 8 GB build/test bursts.
- Firecracker snapshot restore latency is dominated by the amount of memory touched after resume; the 28–50 ms third-party figures are with small, hot snapshots on local NVMe. E2B/CodeSandbox quote 0.5–3 s because they pull diffs from object storage.

### Gaps
- No vendor (Fly, E2B, Modal, Daytona, Vercel, Northflank, Blaxel, CodeSandbox) publishes sandboxes-per-host or overcommit ratios; E2B's `docs/ARCHITECTURE.md` may hold more but was not fetched.
- The original CodeSandbox "How we clone a running VM in 2 seconds" and "cloning microVMs using userfaultfd" posts return HTTP 403 and web.archive.org is blocked; numbers above are from mirrors/summaries.
- Northflank sandbox cold start/density: no primary numbers found.
- Firecracker guest-kernel baseline RSS (kernel + init in a minimal rootfs) was not found in a primary source.

## Key question 2: gVisor and Kata vs plain containers vs microVMs — overhead numbers

### Takeaway
Plain runc containers add essentially zero fixed memory; gVisor adds a Sentry process (tens of MB, example RuntimeClass overhead 50 Mi) and large syscall/network latency penalties; Kata/Firecracker add a guest kernel + VMM (example RuntimeClass overhead 130–200 Mi) and 1.9–2.4 s cold starts via containerd, versus ~0.4 s for Docker/gVisor. The single best density data point is Google's Oct 2026 node-swap benchmark: on one 32 vCPU/120 GB node, 512 runc pods vs 80 gVisor Python-sandbox pods vs 40 Kata headless-Chrome pods (without swap).

### Cited Findings
- Kubernetes RuntimeClass `podFixed` overhead examples (2026-02-09, "measure your own"): Kata 130 Mi / 250m CPU (web 100 Mi, batch 200 Mi); gVisor `runsc` 50 Mi / 100m; `firecracker-containerd` 200 Mi / 300m. A 16 Gi node fits ~16 1-Gi pods without overhead, ~14 with Kata's 130 Mi. — [OneUptime: pod overhead for VM runtimes](https://oneuptime.com/blog/post/2026-02-09-pod-overhead-vm-runtimes-kubernetes/view)
- Measured startup incl. VM init, images cached, bare-metal 8-core Xeon/16 GB, 4 vCPU/4 GB guests (Edera-authored paper, Jan 2025): Docker/runc 381 ms, gVisor (systrap) 444 ms, Kata (Dragonball VMM) 1,913 ms, Firecracker via firecracker-containerd 2,421.8 ms. sysbench CPU: Firecracker 183.8 events/s vs ~330–368 for the others ("roughly half"). nginx ab latency: Docker 15 ms, gVisor 220 ms. — [Edera "Goldilocks Isolation" arXiv 2501.04580](https://arxiv.org/html/2501.04580)
- gVisor's own performance guide: the Sentry "has a mostly fixed memory cost plus a variable amount that scales with resources like sockets and open files"; density test = 50 instances each of sleep/node/ruby; overhead is highest for syscall-bound and small-request workloads (Node/Ruby HTTP "high relative overhead"); systrap platform recommended; most startup overhead "comes from Docker itself." Exact numbers are only in figures/CSVs, not text. — [gVisor performance guide](https://gvisor.dev/docs/architecture_guide/performance/)
- Firecracker VMM memory overhead ~3 MB vs Cloud Hypervisor ~13 MB vs QEMU higher (measured). — [NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Density on one node (Kubernetes blog, 2026-10-05, Google authors; c4-standard-32 = 32 vCPU/120 GB for the runc row): without swap, 512 plain runc pods; 80 gVisor headless-Chrome pods; 40 Kata headless-Chrome pods; 80 gVisor Python sandboxes (~375 MiB resident each). — [Kubernetes blog: Scaling workloads with node swap](https://kubernetes.io/blog/2026/10/05/scaling-kubernetes-workloads-with-node-swap/)
- Older peer-reviewed comparison (Docker, Kata 1.11, gVisor 2020, Firecracker v0.21.1, QEMU/KVM) exists but uses dated versions; only abstract reviewed. — [SciTePress 2021](https://www.scitepress.org/Papers/2021/104405/104405.pdf)

### Inferences
- 512 runc pods on 120 GB ≈ 234 MB/pod all-in, i.e. plain containers on a 48 GB node could host ~200 of your 220–500 MB idle agents *only if* nothing is reserved for bursts — the gVisor/Kata rows (80/40 pods) show that sandboxing runtimes cost 6–13x density on the same box for memory-heavy workloads.
- For your workload (Node agent, lots of small syscalls/file I/O), gVisor's syscall penalty (nginx 15 → 220 ms) is likely to hurt lint/test bursts more than Firecracker's ~half-speed sysbench CPU result suggests; Firecracker's weak point is block I/O throughput, which matters for `npm install`/`git checkout`.

### Gaps
- No single study measures resident memory per instance for runc vs gVisor vs Kata vs Firecracker under identical conditions in 2025–2026; the Edera paper omits memory tables, gVisor's docs omit numbers in text.

## Key question 3: Checkpoint/restore of processes and containers — CRIU, Kubernetes checkpointing status, Firecracker restore, scale-to-zero, restore latency for a Node agent

### Takeaway
Kubernetes container checkpointing (`ContainerCheckpoint`, CRIU via containerd 2.x/CRI-O) is still beta as of v1.34–1.35 with no in-Kubernetes restore path; VM-level snapshot/restore (Firecracker, gVisor) is what production vendors use and delivers ~30–300 ms warm restores locally, 0.5–3 s when diffs come from object storage. Knative/KEDA scale-to-zero is a container cold start (seconds to tens of seconds) and is not suited to interactive agents. No measured CRIU restore latency for a Node process was found.

### Cited Findings
- Kubelet Checkpoint API: feature gate `ContainerCheckpoint`, "Beta since Kubernetes v1.30, enabled by default"; `POST /checkpoint/{namespace}/{pod}/{container}` writes `checkpoint-<pod>-<container>-<ts>.tar` under `/var/lib/kubelet/checkpoints`; "Checkpoint time grows with the container's memory use"; the page "does not describe how to restore a checkpoint through Kubernetes"; runtime must implement CRI checkpoint or returns 500. — [Kubernetes kubelet checkpoint API reference](https://kubernetes.io/docs/reference/node/kubelet-checkpoint-api/)
- Alpha in 1.25, beta in 1.30; works through CRIU with runc/crun/CRI-O/containerd; no `kubectl checkpoint` upstream. — [criu.org/Kubernetes](https://criu.org/Kubernetes). AWS EKS 1.34 ships containerd 2.x with the gate on by default; tested with CRIU 3.17.1. — [AWS blog: forensic container checkpointing on EKS](https://aws.amazon.com/blogs/containers/forensic-container-checkpointing-on-amazon-eks/). No source reports graduation beyond beta as of the v1.34/1.35 docs.
- CRIU basics: dumps process state to files, rebuilds equivalent processes; `pre-dump` iteratively snapshots memory changes. — [criu(8) man page](https://man.archlinux.org/man/criu.8.en). 2016 runc checkpoint/restore benchmark: C/R time grows with memory from ~1 MB to 2.5 GB; a restore shortly after dump is faster because the image is still in page cache. — [CRIU list, runc C/R benchmarking](https://lists.openvz.org/pipermail/criu/2016-June/029265.html)
- Firecracker restore: third-party 28 ms ([dev.to/adwitiya](https://dev.to/adwitiya/how-i-built-sandboxes-that-boot-in-28ms-using-firecracker-snapshots-i0k)) and 49 ms ([PandaStack](https://www.pandastack.ai/blog/microvm-malware-detonation-sandbox/)); Fly suspended Machine resume "a few hundred milliseconds" vs stopped Machine start "about 2 seconds or more" ([Fly docs](https://docs.fly.io/launch/autostop-autostart)); Sprites checkpoint ~300 ms, restore reconnect "well under a second" ([Fly Sprites](https://fly.io/sprites/checkpoint-restore/)); CodeSandbox hibernate resume ~500 ms ([rywalker summary](https://rywalker.com/research/codesandbox-sdk)), Together docs 3 s resume/clone ([Together docs](https://docs.together.ai/docs/together-code-sandbox)); E2B ~1 s resume, ~4 s/GB pause (beta-era mirror) ([Novita mirror](https://novita.ai/docs/guides/sandbox-e2b-sandbox-persistence)); Modal gVisor restore 2.5x faster than cold container start ([Modal](https://modal.com/blog/mem-snapshots)).
- Knative cold start for a simple HTTP server ~5 s, TensorFlow classifier up to 40 s (2019 research). — [arXiv 1903.12221](https://arxiv.org/pdf/1903.12221). KEDA scale-from-zero waits up to one `pollingInterval` (default 30 s) before scaling. — [CAST.ai on KEDA](https://cast.ai/blog/keda-kubernetes-event-driven-autoscaling/). IBM Code Engine (Knative) with min-scale 1: 0.22 s average response regardless of pause. — [IBM blog](https://www.ibm.com/blog/?p=450409)
- Lambda SnapStart: "as low as sub-second startup"; "works best at scale… functions that are invoked infrequently might not experience the same performance improvements." — [AWS SnapStart docs](https://docs.aws.amazon.com/lambda/latest/dg/snapstart.html)

### Inferences
- For a Node agent with 220–500 MB RSS, a local-NVMe Firecracker or CRIU restore should be in the hundreds of ms range (restore time scales with pages touched; the 2016 runc data and the "4 s per GB pause" figure suggest ~1–2 s to *write* a 500 MB checkpoint and well under a second to lazily restore). This is an inference; no measured Node/CRIU number exists in the sources.
- CRIU on plain containers is fragile for agents (open TTYs, sockets to the LLM API, inotify watchers) — the K8s API is still "forensic" (no restore), so a product path on k3s would need to drive CRIU/containerd directly or use VM snapshots instead.

### Gaps
- No measured CRIU checkpoint size or restore latency for a Node.js process; no 2025–2026 CRIU benchmark found.
- No source confirmed whether `ContainerCheckpoint` moved to GA in any 2026 release (1.36/1.37); docs still say beta.

## Key question 4: Linux memory tricks — overcommit, KSM, zram/zswap, cgroup v2 `memory.high`, swap in Kubernetes

### Takeaway
Kubernetes node swap went GA in v1.34 (Aug 2025) with `LimitedSwap` for Burstable pods, and Google's Oct 2026 benchmark shows swap on local NVMe raising density 1.5x (runc), 2–3x (gVisor sandboxes) by paging out idle sandboxes' dormant anonymous memory — the single most directly applicable technique for the "idle 90%" workload. KSM gives ~9% on a real production fleet (Meta: 6 GB of 64 GB) at substantial ksmd CPU cost; zram/zswap compress idle anonymous pages ~2–3:1. cgroup v2 `memory.high` throttles+reclaims instead of OOM-killing, making it the right knob for soft limits.

### Cited Findings

**Swap in Kubernetes**
- "Node swap reached General Availability in Kubernetes v1.34" (released 2025-08-27); relies on cgroup v2. Enable with `failSwapOn: false` and `memorySwap.swapBehavior: LimitedSwap`; "Use Burstable QoS: set memory limits higher than requests." — [Kubernetes blog 2026-10-05: Scaling workloads with node swap](https://kubernetes.io/blog/2026/10/05/scaling-kubernetes-workloads-with-node-swap/), [v1.34 release](https://kubernetes.io/blog/2025/08/27/kubernetes-v1-34-release/)
- Measured results (same post): Linux 6.1.1 kernel build with 600 MB limit → 300 MB limit with swap = −50% RAM and 374 s vs 433 s baseline; cutting to 200 MB pushed the working set into swap: ">40% longer execution time" ("insurance policy for burst memory, not a replacement for active RAM"). Headless Chrome on Kata 40 → 50 pods (+25%); on gVisor 80 → 160 (+100%); Python sandbox on gVisor 80 → 240 (+200%); plain runc on c4-standard-32 (32 vCPU/120 GB) 512 → 768 (+50%). Latency at peak density rose "mainly because pods competed for CPU, not because of swap I/O." Python sandbox resident ≈375 MiB. GKE exposes this as "Node Memory Swap on Local SSD." — [Kubernetes blog 2026-10-05](https://kubernetes.io/blog/2026/10/05/scaling-kubernetes-workloads-with-node-swap/)
- Swap modes: `NoSwap` (default; only system daemons/kubelet may swap) and `LimitedSwap` (per-Pod amount "determined automatically"); applied via cgroup v2 `memory.swap.max` on the container cgroup; metrics `node_swap_usage_bytes`, `container_swap_usage_bytes`, `container_swap_limit_bytes`, `kubectl top … --show-swap`. — [Kubernetes swap memory management](https://kubernetes.io/docs/concepts/cluster-administration/swap-memory-management/), [swap-behavior reference](https://kubernetes.io/docs/reference/node/swap-behavior/)
- PSI (pressure stall) metrics graduated to beta in v1.34 (2025-09-04) — useful for detecting memory pressure under overcommit. — [v1.34 release sidebar](https://kubernetes.io/blog/2025/08/27/kubernetes-v1-34-release/)

**cgroup v2 semantics**
- `memory.high`: "the processes of the cgroup are throttled and put under heavy reclaim pressure… Going over the high limit never invokes the OOM killer and under extreme conditions the limit may be breached." `memory.max`: "If a cgroup's memory usage reaches this limit and can't be reduced, the OOM killer is invoked in the cgroup." `memory.low`: best-effort protection; `memory.min`: hard protection. `memory.swap.max`: caps swap-out of anonymous memory. `memory.zswap.max`: caps a cgroup's zswap pool. `memory.reclaim`: write "1G" to proactively reclaim from a cgroup (optional `swappiness=`); does not signal memory pressure. — [Linux cgroup-v2 admin guide](https://docs.kernel.org/admin-guide/cgroup-v2.html)

**KSM**
- Meta/Instagram production (measured): ~73,000 `pages_shared` referenced by 2.1 million `pages_sharing` → "roughly 6GB saved on a 64GB machine"; `pages_to_scan` default 100 was far too low (4,000–5,000 used); ksmd "up to 60% CPU usage during startup, dropping to around 30% in steady state" on a Skylake host; `prctl(PR_SET_MEMORY_MERGE)` (kernel 6.4) opts in a whole process and is inherited across fork; smart scan (6.7) cuts pages scanned per cycle 10–20%; in-kernel auto-tune advisor cuts ksmd CPU 20–30%. — [LWN: An overview of KSM](https://lwn.net/Articles/953141/)
- KSM "introduces a large overhead in CPU and memory bandwidth usage due to the use of red-black trees and content-based page comparison." — [IEEE NAS 2019](https://computer.org/csdl/proceedings-article/nas/2019/08834730/1dlwnOlPBSw). Savings can be read live from `/sys/kernel/mm/ksm/` (bytes and percent). — [Netdata KSM monitoring](https://blog.netdata.cloud/ksm)
- An unverified podcast listing claims "over 40 percent of RAM" saved for 20 Ubuntu VMs; treat as unreliable. — [Audible listing](https://www.audible.co.uk/pd/B0H7MVHDLN)

**zram / zswap**
- Rules of thumb: ~2:1 for lzo/lz4, ~3:1 for zstd (community guide, not a benchmark). — [Slackware zram HOWTO](https://docs.slackware.com/howtos:slackware_admin:zram_configuration). One user's measurement: zswap ratio 2.82 at normal load, 2.65 under stress; zram 1.14 normal / 4.16 under stress. — [OpenWrt forum](https://forum.openwrt.org/t/optimized-nas-latency-memory-build-for-linksys-ea6350v3-civic/44125/32)
- zram supports marking slots `idle` and, with `CONFIG_ZRAM_WRITEBACK`, writing "idle/incompressible page[s] to backing storage rather than keeping it in memory"; stats in `/sys/block/zram<id>/{stat,io_stat,mm_stat}`. — [Linux zram admin guide](https://docs.kernel.org/6.2/admin-guide/blockdev/zram.html)

**Overcommit**
- AWS Lambda: CPU and memory are "both soft-allocated and oversubscribed… Oversubscription is fundamentally a statistical bet." — [NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)
- Coder's guidance for dev workspaces: "We recommend against over-provisioning memory for developer workloads, as this may lead to OOMKiller invocations." — [Coder scale testing docs](https://coder.com/docs/@v2.36.3/admin/infrastructure/scale-testing)
- Firecracker guests: with `vm.overcommit_memory=0` the guest may refuse large allocations and `deflate_on_oom` does not cover that case; setting 1 is not recommended. — [Firecracker ballooning.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/ballooning.md)

### Inferences
- The Google swap benchmark is the closest published analogue to your workload (idle sandboxes with ~375 MiB resident waiting for prompts): plain containers + NVMe swap + Burstable QoS gave 768 pods on 120 GB (≈160 MB RAM per pod amortized). Scaled to a 48 GB VPS that is ~300 pods *if* the VPS has fast local NVMe and `--max-pods` is raised — but each pod's hard limit still needs to accommodate multi-GB test bursts, so the practical cap is set by how many bursts coincide, not by idle RSS.
- KSM is a weak lever for many Node processes: V8 heaps are mostly unique per process (JIT code, heap objects), so sharing is concentrated in loaded shared libraries and snapshot pages that the page cache already shares; expect single-digit-percent savings as at Meta, at tens of percent of one core for ksmd. zram/zswap for idle agents is a better fit: 220–500 MB of mostly-idle anonymous memory compressed 2–3:1 is 100–200 MB saved per sandbox, and cgroup v2 `memory.high` + `memory.reclaim` can push idle sandboxes into zram deliberately.
- Firecracker free-page reporting + a host swap/zram layer is the VM-world equivalent: it gives the host back pages the guest freed, but cannot compress pages the guest still holds, so the guest must also be tuned (or snapshotted to disk when idle).

### Gaps
- No measurement of KSM savings specifically across many identical Node/V8 processes.
- No measurement of zram/zswap compression ratio on idle Node/V8 heaps.
- The exact LimitedSwap allocation formula (per-container swap ∝ memory request / node memory × total swap) is on a doc page section that was truncated in fetch; verify in the swap-memory-management page before relying on it.

## Key question 5: Storage dedup for many checkouts of one repo — worktrees, alternates, partial clones, overlayfs, reflinks, shared node_modules; the real cost of one more worktree

### Takeaway
A git worktree shares the full object store with its parent, so the marginal disk cost of one more worktree is just the working tree (checked-out files) plus whatever untracked build output and `node_modules` it accumulates — and in practice `node_modules`/vendor dominate: one measured case had 10 worktrees consuming 9.9 GB, 2.8 GB of which was recoverable by hardlinking identical files. pnpm's content-addressable store or reflink-capable filesystems (btrfs/XFS/ZFS) remove most of that duplication; vendors use CoW overlay root filesystems for the same reason.

### Cited Findings
- Partial clones: `--filter=blob:none` (blobless) fetches all commits and trees up front and blobs at checkout; `git log -- <path>` and `merge-base` need no downloads, `git diff`/`git blame` trigger blob fetches on first run; treeless (`--filter=tree:0`) and shallow (`--depth=1`) are recommended only for single-use CI; "full clones for most developers," blobless for very large repos with large historical blobs. No size numbers in the post. — [GitHub blog: partial clone and shallow clone](https://github.blog/open-source/git/get-up-to-speed-with-partial-clone-and-shallow-clone/)
- Worktrees share repository history/objects; pnpm's guide: each worktree gets its own `node_modules` but packages are hardlinked from one global content-addressable store, so a 1 MB dependency used by several projects "occupies disk space once." — [pnpm: git worktrees](https://pnpm.io/git-worktrees), [pnpm FAQ](https://pnpm.io/faq)
- Measured (blog, ext4, 28 GB VPS): "ten worktrees… consumed 9.9 GB, mostly from duplicated node_modules and vendor directories"; running jdupes to hardlink identical files reclaimed 2,833 MB; author restricts hardlinking to gitignored build dirs (npm/Composer write via rename, so hardlinks are safe); reflinks need btrfs, XFS with `reflink=1`, or ZFS and are "the cleaner option." — [ma.ttias.be: deduplicating git worktrees with jdupes](https://ma.ttias.be/deduplicating-git-worktrees-ext4-jdupes/)
- Agent orchestrators symlink `node_modules` and `.env` from the main repo into each new worktree to avoid duplication. — [Composio agent-orchestrator workspace plugin](https://www.mintlify.com/ComposioHQ/agent-orchestrator/plugins/workspace)
- Vendor storage tricks: E2B rootfs is "a copy-on-write overlay over a read-only image, so only touched data is fetched" ([e2b-dev/infra](https://github.com/e2b-dev/infra)); Sprites checkpoints copy "only changed blocks" and bill storage "only for written blocks" ([Fly Sprites](https://fly.io/sprites/checkpoint-restore/)); Modal uses OverlayFS with a FUSE lazy-loading lower layer and skips never-read files like `/usr/share/doc` ([Modal](https://modal.com/blog/mem-snapshots)); Firecracker snapshots allow "read-only disks to be shared among multiple microVMs" ([Firecracker docs](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)).

### Inferences
- Marginal disk for one more worktree ≈ size of checked-out tree + per-worktree `node_modules` (if not shared) + build caches. For a typical TypeScript/Electron app the checkout is tens of MB while `node_modules` is hundreds of MB to >1 GB, so sharing `node_modules` (pnpm store, read-only bind mount, or reflink copy) is the whole game; the `.git` object store cost is ~0 per extra worktree.
- Reflink copies (`cp --reflink`) of a prepared `node_modules` on btrfs/XFS give per-sandbox writability with near-zero disk until a sandbox writes — the closest host-side equivalent to the vendors' CoW overlays, and it also keeps the page cache shared across sandboxes (same physical blocks), which indirectly saves RAM.

### Gaps
- No published measurement of `.git` vs working-tree vs `node_modules` proportions for an incremental worktree; the 9.9 GB/10 worktrees figure is one anecdote.
- No source quantifies page-cache RAM savings from sharing `node_modules` blocks across sandboxes.

## Key question 6: Kubernetes limits on small nodes — pods per node, requests vs actual, Burstable QoS, in-place resize, VPA; alternatives (systemd-nspawn, Docker, Nomad, Firecracker directly, unikernels)

### Takeaway
The 110 pods/node figure is a design/test criterion, not a hard limit — Coder documents 256 workspace pods/node and Google ran 512–768 runc pods on one node — so the real constraints are memory requests (the scheduler packs on requests, not usage) and burst limits. In-place pod resize is GA in v1.35 (Dec 2025) including memory-limit decreases, and pod-level resources resize is beta in v1.36, so requests can now be shrunk/grown for idle vs active agents without restarts. Vendors at scale do not use Kubernetes for the data plane: E2B runs a per-node orchestrator driving Firecracker directly.

### Cited Findings
- Kubernetes v1.37 is designed to accommodate "no more than 110 pods per node," ≤5,000 nodes, ≤150,000 pods, ≤300,000 containers (stated as design criteria; `--max-pods` not discussed on that page). — [Kubernetes: considerations for large clusters](https://kubernetes.io/docs/setup/best-practices/cluster-large/)
- Coder validated architectures: "Maximum number of Kubernetes workspace pods per node: 256"; 1,000-user reference = 64 nodes × 16 workspaces on 8 vCPU/32 GB nodes; planning formula "1 vCPU x 2 GB memory x 1 workspace" (covers idle + occasional builds); idle Coder agent needs 0.1 vCPU and 256 MB; scale nodes at 80% CPU or memory; against memory overcommit. — [Coder scale testing](https://coder.com/docs/@v2.36.3/admin/infrastructure/scale-testing), [Coder 1k-user architecture](https://coder.com/docs/@f05969a/admin/infrastructure/validated-architectures/1k-users)
- Google's node-swap benchmark placed 512 (no swap) and 768 (swap) runc pods on a single c4-standard-32 node, i.e. well above 110. — [Kubernetes blog 2026-10-05](https://kubernetes.io/blog/2026/10/05/scaling-kubernetes-workloads-with-node-swap/)
- In-place Pod resize: alpha v1.27, beta v1.33, "stable (GA) in Kubernetes 1.35" (2025-12-19); 1.35 "lifted the earlier ban on decreasing memory limits, though the check is best-effort." — [Kubernetes 1.35 in-place resize GA](https://kubernetes.io/blog/2025/12/19/kubernetes-v1-35-in-place-Pod-resize-ga/). Pod-level resources beta in 1.34; in-place pod-level resize beta and on by default in v1.36 (2026-04-30). — [Kubernetes v1.36 pod-level resize beta](https://kubernetes.io/blog/2026/04/30/kubernetes-v1-36-inplace-pod-level-resources-beta/), [KEP-5419](https://www.k8s.dev/resources/keps/5419/)
- RuntimeClass `overhead.podFixed` is added to pod requests for scheduling/quota (e.g. 1 Gi request + 130 Mi Kata overhead counts as 1.13 Gi). — [OneUptime: pod overhead](https://oneuptime.com/blog/post/2026-02-09-pod-overhead-vm-runtimes-kubernetes/view)
- Swap only applies to Burstable pods ("set memory limits higher than requests"). — [Kubernetes blog 2026-10-05](https://kubernetes.io/blog/2026/10/05/scaling-kubernetes-workloads-with-node-swap/)
- Alternatives in production: E2B's data plane is an orchestrator process on every node that manages Firecracker VMs, cgroups and network namespaces directly, with "Embed" running the whole stack on one Linux host; Kubernetes is only one deployment option for the control plane. — [e2b-dev/infra](https://github.com/e2b-dev/infra). Fly's autostop loop is explicitly "not suited to thousands of Machines in one app." — [Fly docs](https://docs.fly.io/launch/autostop-autostart). Unikraft Cloud claims scale-to-zero with "no resources" consumed when idle and millisecond cold starts (marketing). — [Unikraft how it works](https://unikraft.cloud/how-it-works)

### Inferences
- On k3s, the levers in order of impact for your 48 GB box: (1) drop the 1 GiB request to the measured idle RSS (~256–512 Mi) and keep a higher limit (Burstable) — the scheduler packs on requests, so this alone moves 8–12 pods toward 60–100; (2) enable `LimitedSwap` on NVMe or zram so idle pods' anonymous memory is paged out; (3) raise kubelet `--max-pods` (k3s `--kubelet-arg=max-pods=…`) above 110 and widen the pod CIDR; (4) use in-place resize (GA 1.35) to grow limits only while an agent is active. VPA was not re-verified in sources and in practice conflicts with in-place resize semantics unless on recent versions.
- Running Firecracker directly (or via `firecracker-containerd`) with snapshot pause/resume is how vendors reach "hundreds per host," but it requires KVM — many VPS products do not expose nested virtualization; check `/dev/kvm` availability before planning this path.

### Gaps
- No primary sources found for systemd-nspawn, Nomad, or plain Docker density comparisons in 2025–2026; no VPA status update found.
- The k3s-specific max-pods ceiling and pod-CIDR sizing were not sourced.

## Key question 7: Densities actually reported — dev containers per box, Coder/Gitpod/Codespaces capacity, Fly's claims, E2B's per-host numbers

### Takeaway
Only three hard, dated numbers exist: AWS's Lambda target of "up to 8000 functions on a server" (2020), Coder's 16 workspaces per 8 vCPU/32 GB node (2 GB per developer workspace, no overcommit), and Google's 512→768 runc pods / 80→240 gVisor Python sandboxes on one 32 vCPU/120 GB node (Oct 2026). Fly, E2B, Modal, Daytona, Vercel and CodeSandbox publish account concurrency limits (100–10,000) but not host densities; Unikraft's "100,000+ per server" is marketing.

### Cited Findings

- Google/Kubernetes (2026-10-05, c4-standard-32 = 32 vCPU/120 GB): runc 512 → 768 pods with swap; gVisor Python sandboxes (~375 MiB resident) 80 → 240; gVisor headless Chrome 80 → 160; Kata headless Chrome 40 → 50. — [Kubernetes blog: node swap](https://kubernetes.io/blog/2026/10/05/scaling-kubernetes-workloads-with-node-swap/)
- Fly's measured Claude Code sandbox: 30% of 2 vCPU and 1.5 GB resident average, bursts to 8 CPUs/8 GB; 100 agents for an hour ≈ $5.93 on Sprites. — [Fly learn article, 2026-10-05](https://fly.io/learn/claude-code-sandbox-cost/). - Account concurrency ceilings (not host density): E2B Pro 100, Pro++ 1,100 ([E2B pricing](https://e2b.dev/pricing)); Vercel Pro 10,000 ([Vercel Sandbox pricing](https://vercel.com/docs/vercel-sandbox/pricing)); CodeSandbox Scale 250 ([rywalker summary](https://rywalker.com/research/codesandbox-sdk)).

- Unikraft: "thousands of instances on a single server" / "100,000+ instances per server" (marketing, no conditions). — [unikraft.cloud](https://unikraft.cloud/how-it-works), [unikraft.io](https://unikraft.io)
- Idle container footprints for planning (docker stats, Ubuntu 24.04): nginx ~8 MB, Redis 7 ~12 MB, PostgreSQL 16 ~45 MB; no Node figure. — [OneUptime Docker Desktop resource guide](https://oneuptime.com/blog/post/2026-02-08-how-to-use-docker-desktop-resource-management-settings/markdown)

### Inferences
- Normalizing the published numbers to a 48 GB box: Coder-style no-overcommit dev workspaces → ~24; Google's runc+swap sandboxes (~160 MB/pod amortized) → ~300; gVisor Python sandboxes with swap (~500 MB/pod amortized) → ~96; Firecracker idle-paused sandboxes → bounded by disk and resume rate, not RAM. "Hundreds of agents per tiny box" is therefore realistic only with idle memory reclaimed (swap/zram or pause-to-disk) and with burst concurrency statistically bounded.
- Fly's 1.5 GB average resident for Claude Code (vs your 220–500 MB measurement) suggests measured RSS depends heavily on whether a dev server, LSP or test watcher is left running inside the sandbox; density planning should be done on your own `docker stats`/PSI data, as Coder and the Docker guide both advise.

### Gaps
- GitHub Codespaces and Gitpod/Ona publish no per-host capacity-planning numbers that I could find.
- No E2B, Modal, Daytona, Vercel, Northflank or Blaxel per-host density figures exist publicly.
- No published "N dev containers per 64 GB box" community benchmark for Node agents specifically.

## Key question 8: Peer-to-peer / edge angles — user's own laptops/phones (Remote Control, Tailscale), Cloudflare Containers/Workers pricing, WebContainers in the browser

### Takeaway
Two zero-server-cost patterns exist: Claude Code Remote Control (research preview Feb 2026) runs the agent on the user's own machine with phone/web as a remote window, and StackBlitz WebContainers run Node.js entirely in a browser tab (free for OSS, commercial license otherwise). ### Inferences
- For a product whose users already run Claude Code locally, Remote Control–style "agent runs on the user's machine, server is a relay" offloads 100% of sandbox compute and sidesteps density entirely; the cost is availability (laptop asleep = agent gone) and no isolation from the user's own files.
- Cloudflare's `lite` instance (256 MiB) at $0.0000025/GiB-s is ~$0.0023/hour while awake and $0 while asleep — the cheapest per-idle-sandbox pricing found, but 256 MiB is below your measured 220–500 MB agent RSS, so `basic` (1 GiB, ~$0.009/hour awake) is the realistic floor.
- WebContainers cannot run native binaries or arbitrary Linux tooling, so they suit browser-side Node tasks (lint, unit tests, Vite builds), not a general coding-agent sandbox with git, compilers and system packages.

### Gaps
- No primary Tailscale/Anthropic documentation on scheduling agent sandboxes onto idle personal devices; the pattern exists only as Remote Control (one machine, one user).
- WebContainers memory limits, native-binary restrictions and commercial pricing were not retrieved from primary pages.
- Cloudflare per-account concurrent-container limits are on a separate Limits page not fetched.
