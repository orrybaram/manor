# Toolchain cost: making lint/typecheck/test/build nearly free for hundreds of agents on one small box

Scope: TypeScript / pnpm / Electron / React stack, as of 2026-10-16. Where a number came from the Manor repo itself (measured on this machine today: Apple Silicon Mac, 24 GB RAM, Node v24.13.0, pnpm 10.23.0, TypeScript ~5.8.3, ESLint ^10.0.3, Vitest ^4.1.0, Vite ^7.0.4, Electron 35.7.5, 1,435 tracked `.ts/.tsx` files, 1,588 files / 197k lines reach the renderer `tsc` program) it is marked **[local measurement]**. Everything else carries an inline source.

## Baseline: what the Manor toolchain actually costs today

### Takeaway
On this repo the renderer `tsc` pass peaks at ~1.15 GB RSS and the Electron pass at ~1.03 GB; a *non-type-aware* ESLint pass (recommended + typescript-eslint non-typed rules + react-hooks + react-refresh) peaks at 2.2 GB RSS and takes 26 s wall / 41 s CPU. ESLint, not tsc, is the dominant memory peak, and it is not because of type-aware rules.

### Cited Findings
- **[local measurement]** `tsc -p tsconfig.json --noEmit` (renderer, 1,588 files, 197,209 lines): 5.99 s real, 8.97 s user, peak RSS 1,148 MB; `--extendedDiagnostics` reports "Memory used: 945,986 K", check time 4.44 s of 5.50 s total.
- **[local measurement]** `tsc -p tsconfig.electron.json --noEmit`: 3.36 s real, peak RSS 1,028 MB. `tsc -p tsconfig.node.json --noEmit` (just `vite.config.ts`): 0.42 s, peak RSS 369 MB. The repo's `typecheck` script runs only the first two (`tsc -p tsconfig.json && tsc -p tsconfig.electron.json`); `tsconfig.json` has `references`, and `tsconfig.tsbuildinfo` / `tsconfig.node.tsbuildinfo` already exist on disk, so some incremental state is in play.
- **[local measurement]** `eslint .` (ESLint 10, flat config, plugins: `@eslint/js`, `typescript-eslint` without `projectService`/`parserOptions.project`, `eslint-plugin-react-hooks`, `eslint-plugin-react-refresh`, `eslint-config-prettier`): 26.35 s real, 40.59 s user, peak RSS 2,227 MB. This is higher than the ~870 MB the assignment quoted; the difference likely reflects an untouched `.eslintcache` (none exists in the repo) and ESLint 10 vs an earlier run, but I could not confirm the cause.
- **[local measurement]** `node_modules` is 1.8 GB (1.4 GB of it in the pnpm virtual store `node_modules/.pnpm`, 872 package directories); the Electron binary alone (`electron/dist`) is 257 MB; the machine-wide pnpm store at `~/Library/pnpm/store/v11` is 13 GB.
- **[local measurement]** Node 24's default V8 heap limit on this 24 GB machine: `v8.getHeapStatistics().heap_size_limit` = 4,288 MB (so a 2.2 GB ESLint peak is well inside the default; the RSS peak is not a heap-limit artefact).

### Inferences
- The three tsc passes are sequential in `pnpm typecheck`, so their memory does not stack (peak ~1.15 GB), but their CPU does (~9.4 s wall). The 3.5 GB / 9.7-core peak the assignment measured for "lint + vitest" is consistent with ESLint at ~2.2 GB plus Vitest's main process and several forked workers running concurrently.
- Because this ESLint config is not type-aware, the oxlint migration path is the simple one (native rules, no tsgolint required); react-hooks is covered natively by oxlint or via its JS-plugin layer at 100% conformance (see next section).

### Gaps
- I did not measure Vitest's peak RSS or worker count on this repo (test run would be longer; the assignment already had a 3.5 GB combined figure).
- I did not run tsgo/oxlint locally (would require installing new packages).

## Native replacements: oxlint, tsgolint, Biome, tsgo, Rolldown/Vite, Vitest vs Jest, Bun test

### Takeaway
Native tools cut wall time 5–100x; published *memory* data is thin. The only rigorous peak-RSS comparison found (TS 6 vs TS 7, Microsoft and an independent M4 test) shows typecheck memory falls only 6–26% in Microsoft's numbers and can even *rise* under tsgo's default 4 checker workers; `--checkers 1` halves it. Oxlint has no published memory numbers but eliminates the Node/V8 process entirely; its CPU time is ~50x lower, which shortens the peak rather than lowering it per se. Jest→Vitest is the one swap with dramatic measured heap savings (10–25x).

### Inferences
- For Manor specifically: replacing ESLint with oxlint (native rules + react-hooks via plugin layer) removes the single largest memory peak (2.2 GB measured locally) and ~40 s of CPU per lint; the published 50–100x speedups suggest sub-second lint with no V8 heap at all. Adding `oxlint --type-aware --type-check` via tsgolint would fold typecheck and lint into one Go process over one program, replacing both ESLint and the two `tsc` passes, but requires TypeScript 7 (Manor is on 5.8.3) and removal of `baseUrl`/non-relative `paths` if used.
- tsgo's default `--checkers 4` trades memory for speed; for a memory-bound box, `--checkers 1` (or `--singleThreaded`) is the right default, and the independent data shows it still delivers 3–5x over tsc at ~30–50% less RSS than the default.
- Jest→Vitest is already done in Manor; the remaining Vitest lever is `--no-isolate` + `threads` + capped `maxWorkers`, which collapses N worker processes' duplicated module graphs into one.

## Incremental and affected-only strategies

### Takeaway
Incremental tooling helps wall time far more than peak memory: `tsc --incremental` still loads the whole program (and single-file gains are graph-dependent and sometimes nil), ESLint `--cache` only skips unchanged files and is unsafe for type-aware/import rules, and Turborepo/Nx affected filtering works at package granularity — Manor is effectively one package, so it gains little. Vitest `--changed`/`--related` is the most directly useful lever for a single-file edit.

### Cited Findings
- TypeScript `--incremental` (since 3.4, 2019) rechecks and re-emits only affected files using `.tsbuildinfo` — [TypeScript 3.4 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-3-4/). Measured single-file results are mixed: n8n saw no speedup (~19.9 s with and without) — [n8n issue #3876](https://github.com/n8n-io/n8n/issues/3876); a Deno contrived test saw 61 s → 59 s for one file but → 19 s for another, depending on graph position — [denoland/deno PR #5094](https://github.com/denoland/deno/pull/5094); a module-federation hyperfine run: base 124 s, full config 5.4 s, incremental 6.0 s (no single-file isolation) — [module-federation/core PR #3506](https://github.com/module-federation/core/pull/3506). Secondary "70–90%" claims have no methodology — [stanza.dev](https://www.stanza.dev/courses/typescript-production/performance-build/typescript-production-compilation-performance)
- ESLint `--cache`: stores per-file results in `.eslintcache`; validity depends on file content/metadata and config; "ESLint does not track dependencies between files," so type-aware rules (`@typescript-eslint`) and import-resolving rules (`eslint-plugin-import`/`import-x`) can be stale — run without cache when accuracy matters; `--cache-strategy content` avoids mtime churn after `git clone`; `--concurrency <n|auto|off>` (default off) lints in worker threads — [ESLint CLI docs](https://eslint.org/docs/latest/use/command-line-interface)
- ESLint v9.34.0 (2025-08-22) introduced `--concurrency`; early testers saw ~1.30x, one 3.01x; `auto` = half the CPU cores for "sufficiently large projects"; containers/CI should re-benchmark — [ESLint blog: multithread linting](https://eslint.org/blog/2025/08/multithread-linting/). (Note: more threads mean more parallel memory, the opposite of what a memory-bound box wants.)
- typescript-eslint: "Running typed linting on a project is generally as slow as type checking that same project"; OOMs are "most often caused by large or complex TypeScript types"; use `projectService`, narrow `include`, avoid `**` in `project` globs; `eslint-plugin-prettier` and `eslint-plugin-import` parse files a second time — [typescript-eslint: typed linting performance](https://typescript-eslint.io/troubleshooting/typed-linting/performance)
- Vitest `--changed [since]` runs tests affected by changed files (e.g. `origin/main`, `HEAD~1`); `--related <files>` runs tests covering listed source files via static imports only (dynamic imports unsupported); `experimental.recordDependencies` records each test's actual loaded modules for more accurate `--changed`; `--maxWorkers` accepts a count or percentage — [Vitest CLI](https://vitest.dev/guide/cli)
- Turborepo `--affected` ≡ `--filter=...[main...HEAD]`, overridable via `TURBO_SCM_BASE`/`TURBO_SCM_HEAD`; package-level by default, task-input level with `futureFlags.affectedUsingTaskInputs`; shallow checkouts mark everything changed; `--concurrency` default 10; `--cache=local:rw,remote:rw` controls read/write per source — [Turborepo run reference](https://turborepo.dev/docs/reference/run)
- Vue-tsc warm `tsbuildinfo` data point: cold 20.4 s vs warm 4.7 s on ComfyUI_frontend (523k lines) — [lilting.ch](https://lilting.ch/en/articles/typescript-7-native-benchmark)

### Inferences
- Incremental tsc does not shrink the memory peak: the whole program must still be parsed and bound to decide what is affected (Manor's ~1 GB per tsc pass would remain). It only trims check time, which on Manor is 4.4 s of 5.5 s.
- For a single-file agent edit on Manor, the highest-yield incremental move is `vitest related <file> --run` (seconds, one worker) plus `oxlint <file>`; typecheck remains whole-program unless served by a daemon (next section).
- Splitting Manor into `main`/`renderer`/`shared` packages would let Turborepo/Nx skip untouched sides, but with ~1,435 files total the per-package programs would each still be hundreds of MB.

### Gaps
- No rigorous public measurement of "single-file edit" savings for tsc `--incremental` on a project of Manor's size; must be measured locally.
- Nx affected-graph numbers for a single-file change were not found in primary sources.

## Remote/shared caching and remote execution; a shared verification service

### Takeaway
Remote caches (Turborepo, Nx) are free or cheap and avoid re-running identical work, but on an agent box every agent's diff is unique, so hit rates on lint/typecheck of *changed* code are near zero — caches help only for the unchanged packages and `node_modules` state. Bazel/Buck2 remote execution is real but heavy for a JS/Electron app. The "one verification service on the box" pattern is architecturally closest to tsgo `--watch`/tsserver-style daemons, not to a build cache.

### Cited Findings
- Turborepo Remote Cache: any HTTP server implementing the open API (`/v8/artifacts`, OpenAPI spec at `/api/remote-cache-spec`) works; community servers `brunojppb/turbo-cache-server`, `ducktors/turborepo-remote-cache`, `Tapico/tapico-turborepo-remote-cache`; Vercel Remote Cache "free on all plans, even if you do not host on Vercel"; caches task outputs and logs; HMAC-SHA256 artifact signing optional — [Turborepo: Remote Caching](https://turborepo.dev/docs/core-concepts/remote-caching)
- Nx self-hosted caching "is now free for everyone" (Nx 20/21/22 docs); official `@nx/s3-cache`, `@nx/azure-cache` etc. are free but require an activation key fetched at install; from Nx 20.8 you can build your own cache server against an OpenAPI spec with no key — [Nx: Self-host your remote cache](https://nx.dev/recipes/running-tasks/self-hosted-caching); [Nx 21 self-hosted caching](https://21.nx.dev/docs/guides/tasks--caching/self-hosted-caching)
- Nx Cloud pricing (page dated 2026-10-15): Hobby free with 50,000 credits/month, 5 contributors, 10 concurrent CI connections, Nx Agents included; Team $29/month incl. $29 credit, add-ons $5.50 per 10,000 credits, $19/contributor, $2.25/concurrent CI connection, $99 dedicated compute cluster with sandboxing; Enterprise custom with single-tenant or fully on-premises deployment; banner claims Nx Agents "4x faster and 30% cheaper than GitHub Actions" (vendor benchmark) — [nx.dev/pricing](https://nx.dev/pricing)
- Bazel remote execution: distributes actions across machines, consistent environment, output reuse; imposes "mandatory configuration constraints"; open gRPC protocol (bazelbuild/remote-apis) — [Bazel: Remote execution overview](https://bazel.build/remote/rbe)
- BuildBuddy (Bazel/Buck2 RBE + cache): Personal free with 100 GB cache transfer and up to 80 Linux RBE cores; Team pay-as-you-go up to 800 Linux cores (per-GB rate shown as placeholder); Mac cores $45/core; open-source MIT self-host plus enterprise on-prem — [buildbuddy.io/pricing](https://buildbuddy.io/pricing); Buck2 is "compatible with BuildBuddy's Remote Cache and RBE" and is hermetic by default — [BuildBuddy docs index](https://docsearch.algolia.com/mcp/docs/repo/buildbuddy-io/buildbuddy)
- Comparison sites describe Buck2/Bazel as suited to "very large, multi-language monorepos" and complex for smaller projects, with Turborepo/Nx the JS-native fit — [Sourcegraph: Best monorepo build tools 2026](https://sourcegraph.com/blog/monorepo-build-tools); [toolradar buck2 vs turborepo](https://toolradar.com/compare/buck2-vs-turborepo)
- Verification as the scarce resource once agents are cheap: Ramp's Inspect write-up argues human review, CI capacity, test quality and release coordination become the bottleneck — [wavect.io on Ramp Inspect](https://wavect.io/de/blog/ramp-inspect-background-coding-agent-infrastructure-2026/); a recommended "single verify command" that detects local/cloud/CI context and prints a machine-readable contract — [Qovery: coding agents broken loop](https://www.qovery.com/blog/coding-agents-broken-loop)

### Inferences
- A content-addressed cache keyed on task inputs only pays off when inputs repeat. For hundreds of agents each holding a different diff of the same repo, the repeating parts are `node_modules` install state and any *unchanged* package in a split monorepo. A shared Turborepo/Nx cache server on the box is nearly free to run and would let agents skip e.g. the Electron-main typecheck when only renderer files changed — but only after Manor is split into packages with separate tsconfig projects.
- A true shared "verification service" (one long-lived typecheck/lint process answering requests for many worktrees) is not what Turborepo/Nx/Bazel provide; it is what tsserver/tsgo `--watch` or an LSP-style daemon provides (next section). Bazel RBE would give per-action isolation and dedup but at the cost of hermetic rule rewrites for Electron/Vite — not justified at Manor's size.

### Gaps
- No source quantified remote-cache hit rates or time saved for agent fleets; Turborepo's docs give only qualitative claims.
- BuildBuddy Team per-GB price is unpublished (placeholder on the page). Nx on-prem price is custom only.

## Long-lived daemons vs cold runs

### Takeaway
Daemons move the cost from "N cold JIT-warmed processes at once" to "one resident process plus cheap requests": eslint_d cuts per-invocation latency ~4–5x; TS 7's watch mode/language service now frees idle type-check state and tunes memory via `--checkers`. Sharing one typecheck daemon across many worktrees is unproven in sources found: tsserver/tsgo are per-project-root, so one daemon per worktree (not per agent run) is the realistic unit.

### Cited Findings
- eslint_d: MacBook Air M1, Node 22.2.0, ESLint 9.8.0: ~500 ms `eslint` vs ~115 ms `eslint_d` for a single file (older docs: 700 → 160 ms); keeps one ESLint instance per working directory, capped at the 10 most-recently-used; clears cache when lockfiles/package.json change; idle exit; no memory figures published — [eslint_d README (npm)](https://npmjs.com/package/eslint_d); [eslint_d README mirror](https://cdn.jsdelivr.net/npm/eslint_d@15.0.2/README.md)
- TS 7 under `--watch` and in the editor "periodically releases unused type-checking state after enough idle time", and the new watcher has "way less CPU usage on idle" than earlier previews — [InfoQ: TypeScript 7 progress](https://www.infoq.com/news/2026/01/typescript-7-progress); 7.0 GA rebuilt `--watch` on a Parcel-watcher port and reports editor open-file-with-error latency 17.5 s → <1.3 s on VS Code — [Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)
- Editor load of the whole VS Code project: 9.6 s (JS tsserver) → 1.2 s (native) — [TypeScript native port announcement](https://devblogs.microsoft.com/typescript/typescript-native-port/)
- Vitest watch: `fsModuleCache` persists transforms across reruns (8.75 s → 5.90 s example) and the main-thread Vite server is shared by all workers — [Vitest: Improving Performance](https://vitest.dev/guide/improving-performance)
- Codex cloud environments keep container state cached for up to 12 hours and resume it per task (shared across the team on Business/Enterprise), rather than rebuilding — [Codex cloud environment docs](https://learn.chatgpt.com/docs/environments/cloud-environment)
- Devin persists workspaces by hypervisor-snapshotting the sandbox VM so sessions "start in seconds without re-downloading modules or re-compiling"; Outposts (July 2026) run sessions on customer infra created from a snapshot, stopped while sleeping — [Modal: Devin Outposts](https://modal.com/blog/devin-outposts-run-devin-in-modal-sandoxes); [Daytona: Devin Outposts](https://www.daytona.io/docs/en/guides/devin/devin-outposts); [fast.io on Devin workspaces](https://fast.io/resources/devin-ai-persistent-workspaces/)

### Inferences
- Memory arithmetic: one resident tsgo watch per worktree at ~0.5–1 GB (TS 7 peak for a ~200k-line program per Microsoft's tldraw/playwright scale, and halved again with `--checkers 1`) replaces two cold ~1.1 GB tsc processes per verification *and* the CPU burst that comes with them; the steady-state cost is the daemon's post-idle-release footprint, which no source quantifies.
- Because tsserver/tsgo programs are rooted at a tsconfig, a daemon cannot trivially serve N worktrees of the same repo; each worktree needs its own program. The cheaper alternative is a *single* worktree per agent with the daemon, and hibernating (SIGSTOP/snapshot) the agent's sandbox when idle, as Devin/Codex do.
- eslint_d becomes moot if oxlint replaces ESLint: a 0.5 s native cold run is already below eslint_d's warm latency.

### Gaps
- No measured RSS for eslint_d, tsserver, or tsgo in watch/idle state was found.
- No source describes a multi-worktree shared TypeScript daemon; it would need to be built (e.g. an LSP proxy) and measured.

## Shared dependency storage: pnpm store, hardlinks, Yarn PnP, Nix

### Takeaway
pnpm already dedups across worktrees on the same filesystem via hardlinks (Manor: 1.8 GB `node_modules` backed by a 13 GB machine-wide store); the per-worktree cost is inodes and symlinks, not bytes. Cross-container sharing requires the store on the same filesystem as every project (otherwise pnpm silently copies). Electron's 257 MB binary is the single largest dedup-able blob.

### Cited Findings
- pnpm stores every package file once in a content-addressable store and hard-links into `node_modules`, "consuming no additional disk space"; a new version that changes 1 of 100 files adds 1 file to the store — [pnpm motivation](https://pnpm.io/motivation)
- Store location: `$PNPM_HOME/store`, else `$XDG_DATA_HOME/pnpm/store`, else `~/Library/pnpm/store` (macOS) / `~/.local/share/pnpm/store` (Linux); "each disk gets its own store" and on a different disk "pnpm will copy packages from the store instead of hard-linking them"; in a sandbox/container where only the project is writable the store falls back to `node_modules/.pnpm-store`; for a network-FS store shared by many machines use `storeIndexFormat: files` to avoid single-machine SQLite locking; shared stores should be writable only by trusted users; locks coordinate only when processes share `XDG_RUNTIME_DIR` — [pnpm settings: store](https://pnpm.io/settings/store)
- Linking "is performed using either hard-links or reflinks (copy-on-write)" depending on filesystem — [pnpm README mirror](https://github.com/weezyade/pnpm/blob/main/README.md)
- **[local measurement]** Manor: `node_modules` 1.8 GB (virtual store 1.4 GB, 872 package dirs), `electron/dist` 257 MB, global store 13 GB (pnpm 10.23.0, store v11).
- Yarn PnP avoids `node_modules` entirely via a Node loader, enabling zero-installs (commit `.yarn/cache` + `.pnp.cjs`); Yarn claims pnpm's layout "cannot correctly represent all dependency trees" with peer deps — [Yarn: Comparisons](https://v6.yarnpkg.com/getting-started/comparisons); [Yarn: Node linkers](https://v6.yarnpkg.com/concepts/node-linkers)
- Nix + Yarn: one Discourse participant reports Yarn's caches are "non deterministic and ... fundamentally incompatible with Nix's approach" (anecdotal) — [NixOS Discourse](https://discourse.nixos.org/t/yarn-plugnplay-and-direnv-packaging/19759)

### Inferences
- With pnpm, N worktrees on one Linux box cost ~N × (symlink/inode overhead) + one 1.4 GB virtual-store set of hardlinks that share blocks with the global store; the marginal disk per worktree is small, but `pnpm install` still spends CPU building the symlink farm (not measured). Mount the global store into every agent container (same filesystem, e.g. a bind mount of one host directory) or pnpm degrades to copying 1.8 GB per worktree.
- Electron's native binary cannot be shared by PnP (it must exist on disk) but is a hardlink under pnpm; for Linux agents that never launch the GUI, `ELECTRON_SKIP_BINARY_DOWNLOAD=1` would remove 257 MB per store, though renderer tests that need `electron` would break (not sourced; an inference from the package's postinstall behaviour).

### Gaps
- No source quantified how much of a typical Electron app's `node_modules` is dedup-able across projects; only Manor's own numbers are available.
- Nix store sharing for Node toolchains across containers was not covered by any source found.

## Memory limits: `--max-old-space-size`, cgroup caps, swap/zram

### Takeaway
Capping V8 at 512 MB–1 GB for Manor's tsc (~950 MB heap used) or ESLint (2.2 GB RSS) will make V8 thrash GC and then die with "Reached heap limit"; a cgroup cap kills it with exit 137 instead. The right move is lowering real demand (native tools, `--checkers 1`, fewer Vitest workers), using `--max-old-space-size-percentage` so Node sizes to the container, and treating zram as a burst absorber only.

### Cited Findings
- Node docs: `--max-old-space-size` "Sets the max memory size of V8's old memory section. As memory consumption approaches the limit, V8 will spend more time on garbage collection"; example "On a machine with 2 GiB of memory, consider setting this to 1536"; `--max-old-space-size-percentage=<1..100>` sets the limit as a percentage of available system memory and takes precedence over the absolute flag; `--max-semi-space-size` default is derived from the memory limit (≤1 MiB at a 512 MiB limit, <16 MiB up to 2 GiB); `NODE_COMPILE_CACHE` stable as of v25.4.0 — [Node.js CLI docs](https://nodejs.org/api/cli.html)
- **[local measurement]** Node 24.13.0 on a 24 GB Mac: default `heap_size_limit` 4,288 MB; the Manor renderer tsc reports ~946 MB "Memory used".
- Two different OOMs: V8 heap-limit (`FATAL ERROR ... Reached heap limit`, exit 134) vs cgroup/OS OOM kill (exit 137); raising `--max-old-space-size` inside a capped container "makes it worse by encouraging Node to allocate more before dying" — [oneuptime: Node heap out of memory](https://oneuptime.com/blog/post/2026-01-22-nodejs-heap-out-of-memory/view)
- Docker: with only `--memory` set, memory+swap defaults to 2× the limit; `--memory-swap` equal to `--memory` disables swap; runtimes like Node may size heaps from host memory rather than the cgroup, causing kills "despite free heap space" — [Netdata: Docker memory limits](https://www.netdata.cloud/guides/docker/docker-memory-limits/)
- cgroup v2 `memory.swap.max` caps swap per workload; with swap allowed, inactive anonymous pages can go to zram instead of triggering the OOM killer; kernel developers caution zram "only compresses data while still storing them in RAM", so under sustained pressure RAM fills with compressed pages — [fdcservers: Linux memory management](https://fdcservers.net/blog/linux-memory-management-swap-oom-killer-and-cgroups); [LKML: memsw thoughts](https://lkml.iu.edu/hypermail/linux/kernel/1409.1/00186.html)
- Typed-lint OOMs in practice: Next.js CI raised `NODE_OPTIONS=--max-old-space-size=8192` for its type-aware ESLint job — [vercel/next.js commit](https://app.semanticdiff.com/gh/vercel/next.js/commit/a6f9167c2de0a93f7e907a6c76ca257874a2fd36); typescript-eslint's docs cite `--max-old-space-size=8192` and `--max-semi-space-size=256` as the knobs, but say to reduce complex types first — [typescript-eslint performance](https://typescript-eslint.io/troubleshooting/typed-linting/performance)
- tsc on a leaking/huge program consumes "whatever ceiling was set before crashing" — [TypeScript issue #18411](https://github.com/Microsoft/TypeScript/issues/18411)

### Inferences
- V8 heap is only part of RSS (Manor tsc: 946 MB heap vs 1,148 MB RSS; ESLint RSS 2.2 GB). A 1 GB `--max-old-space-size` would break Manor's `tsc` outright and a 512 MB cap would break everything JS-based in the toolchain; caps are a guardrail against runaway processes, not a way to make the work fit.
- Peaks are short (tens of seconds) and highly compressible (type-checker object graphs), so zram-backed swap is a reasonable way to over-commit *if* agents' bursts are staggered; it is not a fix if hundreds of agents verify simultaneously. A per-box verification semaphore (e.g. allow K concurrent heavy jobs) is the complementary control; no source benchmarked this specifically.

### Gaps
- No measured data on tsc/eslint behaviour under a tight `--max-old-space-size` short of crashing (GC-thrash slowdowns), nor on zram compression ratios for V8 heaps.

## Skipping local verification: central CI/verifier, runner costs, latency

### Takeaway
The pattern exists (agents produce diffs; CI runs checks) but every team reporting on it calls CI "miserable ergonomics for an agent" because of minutes-long batch loops, and converges on pre-warmed, snapshot-restored sandboxes instead. Hosted Linux CI is cheap ($0.002–0.006/min; self-hosted is free of GitHub fees after the March 2026 charge was postponed), so cost is not the obstacle — latency and loss of interactive debugging are.

### Cited Findings
- GitHub-hosted runner rates (private repos): Linux 1-core $0.002/min, Linux 2-core x64 $0.006, Linux 2-core arm64 $0.005, Windows 2-core $0.010, macOS 3–4 core $0.062; free minutes: Free 2,000, Pro/Team 3,000, Enterprise Cloud 50,000; "GitHub Actions usage is free for self-hosted runners" — [GitHub Docs: About billing for GitHub Actions](https://docs.github.com/en/billing/managing-billing-for-your-products/about-billing-for-github-actions)
- GitHub's planned $0.002/min self-hosted runner platform fee (announced 2025-12-16 for 2026-03-01) was postponed "to take time to re-evaluate"; hosted price cuts of up to 39% took effect 2026-01-01; GitHub said it "missed the mark" — [GitHub Changelog: Update to GitHub Actions pricing](https://github.blog/changelog/2025-12-16-coming-soon-simpler-pricing-and-a-better-experience-for-github-actions/); [GitHub resources: 2026 pricing changes](https://resources.github.com/actions/2026-pricing-changes-for-github-actions/). Third-party coverage disagrees on whether "postponed" means cancelled — [SAMexpert](https://samexpert.com/github-actions-pricing-backlash-2026/)
- Self-hosted runner compute: ~$0.001–0.002/min amortised on EC2; a spot c5.4xlarge ~$130/month — [cicdcost.com runner cost](https://cicdcost.com/runner-cost); [openmetal self-hosted runner cost math](https://openmetal.io/resources/blog/the-real-cost-math-behind-self-hosted-github-actions-runners/)
- Buildkite bills per user ($30/user/month Pro) with bring-your-own agents and unlimited minutes; hosted agents ~$0.50–0.80/hour (third-party figure) — [cicdcost build minutes](https://cicdcost.com/build-minutes-cost); [guptadeepak CI/CD platforms 2026](https://guptadeepak.com/tools/top-5-ci-cd-platforms-2026/)
- Agent-fleet practitioner (Agent Sandbox K8s CRD author): verification "has been the hardest" of plan/implement/verify; GitHub Actions for verification had "miserable ergonomics for an agent" — batch execution, slow feedback, no interactive debugging; wants agents to claim pre-warmed sandboxes with stable identities that hibernate when idle — [Hacker News item 49125061](https://news.ycombinator.com/item?id=49125061)
- Docker's "Fleet" (2026-05-01): 7 agent roles run inside microVM Coding Agent Sandboxes on GitHub Actions runners (macOS for issue-fix and weekly architect runs; macOS+Windows nightly CLI tests); PR review spins up 3 runners (macOS/Linux/Windows); worker/reviewer loop up to 5 iterations; first-draft PR "often within the hour"; CI debug cycles are "minutes per iteration" with some CI-only issues costing "hours of wall-clock time"; costs and runner sizing not disclosed — [Docker blog: A Virtual Agent team at Docker](https://www.docker.com/blog/a-virtual-agent-team-at-docker-how-the-coding-agent-sandboxes-team-uses-a-fleet-of-agents-to-ship-faster/)
- Codex cloud (legacy environments doc): `universal` image, setup scripts with internet, agent internet off by default via HTTP(S) proxy, container state cached up to 12 h and resumed per task, auto-installs for npm/yarn/pnpm, agent reads `AGENTS.md` for lint/test commands; CPU/memory limits not documented — [Codex cloud environment docs](https://learn.chatgpt.com/docs/environments/cloud-environment)
- Anthropic Claude Code sandboxing: OS-level sandboxes (Seatbelt on macOS, Bubblewrap on Linux) cut permission prompts 84% internally; open-source `anthropic-experimental/sandbox-runtime`; Claude Code on the web clones the repo into an Anthropic-managed VM with credentials held outside the sandbox behind a proxy — [Anthropic Engineering: Claude Code sandboxing](https://anthropic.com/engineering/claude-code-sandboxing); [InfoQ](https://www.infoq.com/news/2025/11/anthropic-claude-code-sandbox); [eWeek](https://eweek.com/artificial-intelligence/anthropic-claude-code-launch). No Anthropic source describes how builds/tests are made cheap inside those VMs.
- Nx Agents: vendor claim of "4x faster and 30% cheaper than GitHub Actions" — [nx.dev/pricing](https://nx.dev/pricing)

### Inferences
- Economics of batching: at $0.006/min for a 2-core Linux runner, a 2-minute Manor verification (tsc ×2 + lint + vitest) costs ~$0.012; hundreds of agents verifying hourly is dollars per day. The constraint is not money but the 1–5 minute round trip and the loss of "run one test and look," which every practitioner source flags.
- A hybrid is the pattern the sources converge on: agents run *cheap, native, affected-only* checks locally (oxlint on changed files, `vitest related`), and a central verifier (self-hosted runner on the same or a sibling box, or a Turborepo/Nx-cached pipeline) runs the full matrix on the diff before merge. That central verifier can hold the only full toolchain, so agent pods ship with just git, Node (or Bun) and native binaries.

### Gaps
- No team publishes per-agent CPU/memory sizing or measured CI-vs-sandbox latency distributions for agent verification; all latency statements are qualitative ("minutes", "within the hour").
- No Anthropic, OpenAI, Cognition, Factory or Sourcegraph Amp engineering post about build/verification *cost* infrastructure was found; Codex and Devin docs cover snapshots/caching only.
