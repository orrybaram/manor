# Idle RAM, not cores, caps Manor's agents

As of October 2026, the limit on running Manor-sized projects inside Manor's own pods is **memory held by idle processes and reserved by scheduler requests, not CPU and not GPU**. Nothing in a Manor pod touches a GPU; inference happens at Anthropic and shows up on the bill as tokens, and Claude Code's own system requirement is "4 GB+ RAM" with no accelerator ([Claude Code setup docs](https://code.claude.com/docs/en/setup)). CPU is a burst problem that the no-CPU-limit pod spec already solves: an agent averages **0.01–0.08 cores idle and about 0.26 cores while editing**, yet a `pnpm lint` plus test run spikes to **9.7 cores and 3.5 GB** for tens of seconds ([measured_usage.md](../research_notes/Budget%20VPS%20hosts%20for%20k3s/measured_usage.md)). Memory is the problem because every pod requests 1 GiB and may burst to 4 GiB ([kubernetes.ts](../electron/backend/providers/recipe-templates/kubernetes.ts)) for a Claude Code process that holds **180–700 MB whether or not anyone is typing**, plus an 80 MB host server, a daemon, a PTY subprocess per pane, one ~60 MB MCP child per session and a copy of the toolchain, so a 48 GB VPS tops out at roughly **8–12 projects**. Hundreds of agents on a tiny box is reachable in two stages. Shipping Kubernetes features (requests sized to idle RSS, Burstable QoS with node swap, which went GA in v1.34, and in-place resize, GA in v1.35) take a 48 GB node to **low hundreds of parked agents**, following Google's measured 512→768 runc pods on one 120 GB node ([Kubernetes blog](https://kubernetes.io/blog/2026/10/05/scaling-kubernetes-workloads-with-node-swap/)). The pie-in-the-sky stage moves the agent's "brain" off the box entirely, as Anthropic's Managed Agents self-hosted worker already does with a **12 MB Go binary that needs only bash and outbound HTTPS** ([Anthropic docs](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes)), pauses idle sandboxes to zero RAM with snapshot restores of 28–150 ms, and shares one repo image, one dependency store and one native typechecker across every agent. That redesign would overturn **ADR-235 (pod per project), ADR-229 D2/D3/D5 (recipe=host, one kubectl process per stream, "never snapshot a host"), ADR-229's no-automatic-resume scope and ADR-234's per-pod agent install**, and would stretch ADR-227's host-is-the-authority model. The cost accounting is lopsided: sandbox compute is **1–15% of an agent-hour** and the whole Contabo box costs about $0.04/hour, while **tokens are the floor**. "Near zero" compute is effectively already here; near-zero *cost* for agent-made code changes has to come from token levers (model routing, cache hits, fewer turns), from hardware the developer already owns, and from vendors absorbing sandboxes into subscriptions.

## Memory requests, not CPU or GPU, cap today's pods at a dozen per box

Manor's remote pod is a StatefulSet of one with a 20 Gi ReadWriteOnce PVC, a 500m CPU request with no CPU limit, a 1 GiB memory request and a 4 GiB memory limit; the code comment explains the limit: "memory spikes to ~3.5 GiB linting a large repo, so the limit sits well above the request" ([kubernetes.ts](../electron/backend/providers/recipe-templates/kubernetes.ts)). Those defaults came from a 180-second sample of nine Claude Code agents on the author's dev box: idle agents at **220–500 MB and under 0.1 cores**, active agents averaging 560 MB with a 1.4 GB peak, and the lint-plus-test agent peaking at **3,527 MB and 9.67 cores** while averaging 0.45 cores ([measured_usage.md](../research_notes/Budget%20VPS%20hosts%20for%20k3s/measured_usage.md)). The earlier VPS report built on exactly this shape: buy RAM, not cores, and expect 8 pods on 24–48 GB ([Budget VPS hosts for k3s](Budget%20VPS%20hosts%20for%20k3s.md)).

The scheduler packs on requests, not usage, so **1 GiB × N pods is the real ceiling** regardless of how idle the agents are: on a 48 GB node that is roughly 40 pods before the host server, k3s and the OS, and the earlier report's realistic estimate of concurrent lint bursts brought it down to 8–12 ([Budget VPS hosts for k3s](Budget%20VPS%20hosts%20for%20k3s.md)). ADR-234's written Medium preset (2 CPU / 4 GiB requests) was even worse, forcing a 16 vCPU / 32 GiB node for eight pods before commit `31971482` replaced it with the measured sizes ([adr-234](../docs/decisions/adr-234-guided-host-templates/index.md)). GPU never enters this arithmetic. The pod image is `node:22-bookworm-slim` plus git, gh, python3, make and g++ ([Dockerfile](../docker/host-image/Dockerfile)); the only GPU-shaped cost in the system is the model's, paid per token at Anthropic. The research found no evidence that local inference on the box is on the table, and nothing in the notes supports it, so GPU is a non-constraint for Manor today and would become one only if the design changed to self-hosted models.

The verification gate is what sets the 4 GiB limit, and it is heavier than the earlier 870 MB figure suggested. Measured on this repo today, the renderer `tsc` pass peaks at **1,148 MB RSS**, the Electron pass at 1,028 MB, and a *non-type-aware* `eslint .` (ESLint 10, flat config, typescript-eslint without `projectService`) takes 26 s wall / 41 s CPU and peaks at **2,227 MB** ([toolchain_cost.md](../research_notes/Hundreds%20of%20agents%20on%20tiny%20boxes/toolchain_cost.md)). The discrepancy with the 870 MB from the WSL2 sample is unexplained (no `.eslintcache` exists in the repo; ESLint version differs), so the honest planning number is the higher one. The 3.5 GB combined peak is consistent with ESLint at 2.2 GB running alongside Vitest's main process and forked workers. Every pod carries its own copy of this toolchain, Node 22, the g++ compile fallback for node-pty, a `~/.local` Claude Code install and the Manor host package, all stateless and all duplicated by design under ADR-234 D11 and ADR-229 D8 ([manor_constraints.md](../research_notes/Hundreds%20of%20agents%20on%20tiny%20boxes/manor_constraints.md)). The image is about 450 MB compressed, and `node_modules` for Manor itself is 1.8 GB with 872 package directories in the pnpm virtual store ([toolchain_cost.md](../research_notes/Hundreds%20of%20agents%20on%20tiny%20boxes/toolchain_cost.md)).

| Resource | Idle agent | Active agent | Lint + test burst | What binds |
|---|---|---|---|---|
| CPU | 0.01–0.08 cores | ~0.26 cores (p95 1.7) | 9.67 cores max | Nothing; no CPU limit, bursts borrow idle cores |
| Memory | 220–500 MB | ~560 MB, 1.4 GB peak | 3.5 GB peak | **Yes**: 1 GiB request × pods, 4 GiB limit per pod |
| GPU | none | none | none | Not used on the box; paid as tokens |
| Disk | 20 Gi PVC, bills while stopped | same | `node_modules` 1.8 GB per worktree without a shared store | Secondary; local-path does not enforce the claim |

## An agent process is idle 90% of its life but holds 200–700 MB throughout

The per-agent memory is Claude Code itself, not the JS runtime. A do-nothing Node 24 process is ~39 MB and Bun ~18–20 MB; `--jitless` and `--max-old-space-size` change idle RSS by zero ([agent_runtime_footprint.md](../research_notes/Hundreds%20of%20agents%20on%20tiny%20boxes/agent_runtime_footprint.md)). Claude Code 2.1.301 is a **239 MB Bun-compiled native binary** that does not use the host's Node at runtime ([Claude Code setup docs](https://code.claude.com/docs/en/setup)). Its session RSS has been reported at **181 MB fresh, 320 MB thirty seconds after `claude -c`, and 658 MB at the end of a multi-hour session** ([anthropics/claude-code #98420](https://github.com/anthropics/claude-code/issues/98420)), with idle sessions holding 250–350 MB because "its whole state is in its transcript" ([#102115](https://github.com/anthropics/claude-code/issues/102115)). An independent container study puts the headless baseline at **about 185 MB, so 64 concurrent instances need about 12 GB for framework baselines alone**, with per-task peaks from 197 MB to 4 GB and CPU averaging 7.6–13.2% of one core ([arXiv 2602.09345](https://arxiv.org/html/2602.09345v3)). Five live sessions on the author's Mac measured 340–672 MB each after 1.5–17 hours ([agent_runtime_footprint.md](../research_notes/Hundreds%20of%20agents%20on%20tiny%20boxes/agent_runtime_footprint.md)).

Hidden multipliers sit beside each session. Every stdio MCP server is its own Node process at roughly 50–75 MB (Manor's own `mcp-webview-server.js` measured 54–64 MB per session), spawned per session with no sharing, so cost scales as sessions × servers ([claudeissues 45880](https://claudeissues.com/issue/45880-bug-multiple-concurrent-sessions-multiply-mcp-server-processes-without-memory-li)); each session also holds every server's tool schema in its own heap, which one user with ~15 servers found scaled RAM "linearly with (open chats × enabled servers)" ([#88524](https://github.com/anthropics/claude-code/issues/88524)). Claude Code's background daemon pre-spawns `bg-spare` worker pairs, **7–8 pairs at about 1.6 GB** in one report, some 41 hours old ([#99931](https://github.com/anthropics/claude-code/issues/99931)). Off-heap leak regressions have been filed repeatedly in 2026, including RSS growing 400–500 MB/min while idle to 6–7.5 GB, 99% anonymous memory, exceeding the V8 heap cap without a V8 OOM ([#67433](https://github.com/anthropics/claude-code/issues/67433)); the only reliable ceiling is a cgroup `memory.max`, which is what Manor's 4 GiB limit is.

Manor adds its own per-pod tax. Each pod runs `supervise`, the daemon and the host server as separate processes ([docs/remote-hosts.md](../docs/remote-hosts.md)); the host server alone is ~80 MB RSS, dials an always-on relay WebSocket, ticks the agent-status driver every 10 s, polls winsize every 2 s and branch state every 2 s per watched workspace ([manor_constraints.md](../research_notes/Hundreds%20of%20agents%20on%20tiny%20boxes/manor_constraints.md)). Every PTY is its own forked Node subprocess polling the foreground process with `pgrep` every 500 ms, and each of 12 registered hook events, including every `PreToolUse` and `PostToolUse`, spawns a `sh` then a `node` ([agent-connectors.ts](../electron/agent-connectors.ts); [pty-subprocess.ts](../electron/terminal-host/pty-subprocess.ts)). At hundreds of agents, two process spawns per tool call become a fork-rate cost, and the laptop side scales too: the exec transport has no connection multiplexing, so "ten running pods means about thirty `kubectl` processes on the laptop" ([adr-235](../docs/decisions/adr-235-pod-per-project/index.md)).

All of this memory is held for processes that are mostly waiting. TraceLab's ~4,300 real Claude Code and Codex sessions show an **average 46.7 minutes between user requests (median 1.4 min)**, ~13 s per LLM generation and ~18 s per tool call, with 61% of tool calls under a second ([TraceLab](https://syfi.cs.washington.edu/blog/2026-06-25-tracelab/)); its session-level split attributes **92.3% of wall-clock to human thinking**, 3.3% to generation and 4.8% to tools ([TraceLab session timing](https://tracelab.cs.washington.edu/exp/session/session_timing_distribution/)). Within an active turn, LLM time is 40–45% and tools 13–24% ([arXiv 2602.09345](https://arxiv.org/html/2602.09345v3)). Manor never suspends any of it: idle stop runs only from an awake desktop, `requires_input` counts as busy so an overnight prompt keeps a pod up indefinitely, and "Resuming agents by themselves after a reboot" is explicitly unsupported ([docs/remote-hosts.md](../docs/remote-hosts.md); [host-idle-stop.ts](../electron/backend/host-idle-stop.ts)). The one tail that matters for any suspend design is the 4% of tool calls over a minute that account for ~85% of tool time and produce the 15× memory peaks: a design can park agents between turns but must still permit multi-GB bursts inside a turn.

## Shipping levers alone take a 48 GB node from 12 pods to a few hundred parked agents

Nothing in Kubernetes caps a node at 110 pods; that is a design criterion ([Kubernetes large clusters](https://kubernetes.io/docs/setup/best-practices/cluster-large/)), Coder documents **256 workspace pods per node** ([Coder scale testing](https://coder.com/docs/@v2.36.3/admin/infrastructure/scale-testing)), and the real constraints are requests and burst limits. Google's October 2026 benchmark is the closest published analogue to Manor's workload: on one 32 vCPU / 120 GB node, **512 plain runc pods without swap became 768 with NVMe swap**, gVisor Python sandboxes at ~375 MiB resident went 80→240, and latency at peak density rose "mainly because pods competed for CPU, not because of swap I/O" ([Kubernetes blog](https://kubernetes.io/blog/2026/10/05/scaling-kubernetes-workloads-with-node-swap/)). That is ~160 MB of RAM per pod amortized, which normalizes to **~300 pods on a 48 GB VPS**, provided the node has fast local NVMe and `--max-pods` is raised. Node swap is GA since v1.34 with `LimitedSwap` for Burstable pods, i.e. limits above requests ([Kubernetes v1.34](https://kubernetes.io/blog/2025/08/27/kubernetes-v1-34-release/)), and in-place pod resize is GA in v1.35 including memory-limit decreases ([Kubernetes v1.35](https://kubernetes.io/blog/2025/12/19/kubernetes-v1-35-in-place-Pod-resize-ga/)), so requests can grow while an agent is active and shrink when it parks, without a restart.

The ordered k3s levers, none of which touch an accepted ADR, are: drop the memory request from 1 GiB to the measured idle RSS (256–512 Mi) and keep the 4 GiB limit, which alone moves the scheduler ceiling from ~40 to 100–180 pods on 48 GB; enable `LimitedSwap` on NVMe or zram so idle sessions' anonymous memory pages out (zram compresses idle anonymous pages roughly 2–3:1, so 220–500 MB of idle agent becomes 100–200 MB) ([Slackware zram HOWTO](https://docs.slackware.com/howtos:slackware_admin:zram_configuration)); use cgroup v2 `memory.high`, which throttles and reclaims instead of OOM-killing, plus `memory.reclaim` to push parked agents into swap deliberately ([cgroup-v2 admin guide](https://docs.kernel.org/admin-guide/cgroup-v2.html)); and raise `oom_score_adj` on idle sessions so they die first and come back via `--resume` ([#102115](https://github.com/anthropics/claude-code/issues/102115)). KSM is a weak lever for many V8 processes: Meta's production fleet saved ~9% (6 GB of 64 GB) at 30–60% of a core for `ksmd` ([LWN](https://lwn.net/Articles/953141/)). Coder's advice against memory overcommit for developer workloads is the counterweight ([Coder scale testing](https://coder.com/docs/@v2.36.3/admin/infrastructure/scale-testing)): swap is "insurance for burst memory, not a replacement for active RAM," and Google saw >40% slowdown when the working set itself spilled.

The toolchain levers are at least as large, because they shrink the burst that sets the 4 GiB limit. Replacing ESLint with oxlint removes the single biggest peak (2.2 GB measured) and roughly 40 s of CPU per lint: oxlint runs **50–100× faster than ESLint**, and its JS-plugin layer passes 100% of 5,007 `eslint-plugin-react-hooks` tests ([Oxc v1.0](https://oxc.rs/blog/2025-06-10-oxlint-stable); [Oxlint JS plugins](https://oxc.rs/blog/2026-03-11-oxlint-js-plugins-alpha)); Manor's config is not type-aware, so the migration is the simple one. TypeScript 7's native compiler is GA since 2026-07-08 and runs 8–12× faster, but its memory story is mixed: Microsoft reports 6–26% lower peaks, while an independent M4 run saw RSS *rise* under the default four checker workers and fall to 0.8 GB with `--checkers 1` ([Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/); [lilting.ch](https://lilting.ch/en/articles/typescript-7-native-benchmark)). Manor is on TypeScript 5.8.3, so this is a migration with config breakage (`baseUrl`, non-relative `paths`). Vitest's `--no-isolate`, `threads` pool and capped `maxWorkers` collapse N duplicated module graphs into one ([Vitest performance guide](https://vitest.dev/guide/improving-performance)), and `vitest related <file>` plus `oxlint <file>` is the right per-edit check. The pnpm store already hard-links across worktrees, but only on the same filesystem; mount one host directory into every container or pnpm silently copies 1.8 GB per worktree ([pnpm store settings](https://pnpm.io/settings/store)). Finally, a per-box verification semaphore (allow K concurrent heavy jobs) bounds how many 3.5 GB bursts can coincide, which is what actually decides the pod count.

One product-level change belongs in this stage even though it reverses an ADR: **collapse N project pods into one host**. ADR-227 already treats a host as a container of many projects ("The host server is the authority for its host"), and before ADR-235 "People put every workspace of a project there … and often several projects too" ([adr-227](../docs/decisions/adr-227-host-ownership-flip/index.md); [adr-235](../docs/decisions/adr-235-pod-per-project/index.md)). Many projects per pod removes the per-pod 80 MB server, daemon, relay socket, pollers and duplicate toolchain, and the per-pod 1 GiB request, without any code-architecture change; it gives up ADR-235's isolation and per-project idle stop.

## Hundreds on a tiny box means the brain leaves the box and idle agents leave RAM

The pie-in-the-sky design has three moves, and every component ships today somewhere, though nobody has assembled them for a product like Manor. The first is the brain/hands split. Anthropic's Managed Agents self-hosted environment "acts as a work queue … Claude runs on Anthropic's side and requests tool calls. Your worker runs each call locally and posts the result back"; the worker needs "a Linux host … `/bin/bash` at that exact path" and "only outbound HTTPS" ([Self-hosted sandboxes](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes)). The reference worker is the Go `ant` CLI, **12 MB compressed** ([anthropics/anthropic-cli releases](https://github.com/anthropics/anthropic-cli/releases)), and the documented "sandbox per session" pattern starts a fresh container that "reads session details from environment variables, handles that session, and exits" ([Deploy self-hosted workers](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes-workers)). This is the memory that dominates Claude Code (transcript, tool schemas, bundle) moving off the box; what stays is a shell, git and an HTTPS poller at tens of MB, where Go daemons of this class run at single-digit to low-tens of MB ([agent_runtime_footprint.md](../research_notes/Hundreds%20of%20agents%20on%20tiny%20boxes/agent_runtime_footprint.md)). The Agent SDK does not help here: it "runs the Claude Code binary," so an SDK agent costs a full CLI session ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)). The alternative to Anthropic's control plane is Manor's own loop against the Claude API with the same thin executor, which keeps the architecture but puts the orchestration burden on Manor.

The second move is zero RAM for idle agents. Firecracker's VMM overhead is **about 3 MB per microVM**, boots in under 125 ms, and AWS targeted "up to 8000 functions on a server" by soft-allocating oversubscribed resources as "a statistical bet" ([Agache et al., NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-agache.pdf)). Every sandbox vendor uses the same four techniques: restore from a pre-booted memory snapshot instead of booting a kernel, lazily page it in via `userfaultfd` so many VMs share read-only pages, copy-on-write rootfs over a shared image, and pause idle VMs to disk ([e2b-dev/infra](https://github.com/e2b-dev/infra); [Firecracker snapshot docs](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)). Restore latencies run from **28 ms** for a hot local snapshot ([dev.to/adwitiya](https://dev.to/adwitiya/how-i-built-sandboxes-that-boot-in-28ms-using-firecracker-snapshots-i0k)) to ~150 ms (E2B), 100–500 ms (Fly Sprites warm wake) and 1–3 s (Cloudflare) ([Upstash comparison](https://upstash.com/blog/ai-agent-sandbox-providers-compared-2026)); GKE's snapshot-suspend of idle agents cut compute ~40% typically and up to 90% ([ZenML LLMOps DB](https://www.zenml.io/llmops-database/high-performance-agent-infrastructure-with-gke-sandboxing-and-snapshots)). With a 46.7-minute average gap between turns, a parked agent costs disk only, and the practical cap on a 48 GB box becomes the number of *simultaneously awake* agents times their burst, not the number of agents. Two catches: Firecracker needs `/dev/kvm`, and the cheapest VPS hosts in the earlier report, Contabo included, expose no nested virtualization, so this path needs a dedicated box (ReliableSite's 16-core/64 GB EPYC at $99/mo) or a KVM-capable cloud ([Budget VPS hosts for k3s](Budget%20VPS%20hosts%20for%20k3s.md)). And Kubernetes' own container checkpointing is still beta with no in-Kubernetes restore path ([kubelet checkpoint API](https://kubernetes.io/docs/reference/node/kubelet-checkpoint-api/)), so on k3s this means driving Firecracker or CRIU directly, as E2B's per-node orchestrator does rather than using Kubernetes for the data plane ([e2b-dev/infra](https://github.com/e2b-dev/infra)).

The third move is sharing everything that is not the diff. Google's CitC keeps the average workspace at "less than ten files" by layering edits over a shared repo image ([Piper](https://en.wikipedia.org/wiki/Piper_(source_control_system))); Meta's EdenFS populates files on demand but "is not yet supported for external usage" ([facebook/sapling](https://cdn.jsdelivr.net/gh/facebook/sapling@main/README.md)). The shipping approximation for a git repo is one warm blobless clone per node, per-agent `git worktree` with sparse checkout, and a shared read-only `node_modules` via the pnpm store or a reflink copy on btrfs/XFS, since one measured case had **10 worktrees consuming 9.9 GB, mostly duplicated `node_modules`** ([ma.ttias.be](https://ma.ttias.be/deduplicating-git-worktrees-ext4-jdupes/)). Verification becomes a service: one warm `tsgo --watch` daemon per repo answering "check these files against worktree W" over a socket, instead of two cold 1.1 GB `tsc` processes per agent per turn, is the fleet analogue of CitC's shared backend, and every component (tsgo, LSP, worktrees) ships even though no product does this ([reshaped_dev_loop.md](../research_notes/Hundreds%20of%20agents%20on%20tiny%20boxes/reshaped_dev_loop.md)). Google's TAP found that of 5.5 million affected tests "only 63K ever failed; the rest never failed even once," a 99:1 pass ratio that justifies running the full suite on batched milestones rather than per agent ([Memon et al., ICSE-SEIP 2017](https://web.eecs.umich.edu/~xwangsd/courses/w23/readings/googletest.pdf)); Uber's speculative SubmitQueue cut land time 74% ([Uber Engineering](https://www.uber.com/en-US/blog/bypassing-large-diffs-in-submitqueue/)). A fully checkout-less agent is possible via the GitHub Trees API, which accepts inline file content against a `base_tree` ([GitHub REST docs](https://docs.github.com/en/rest/git/trees)), but nothing can run `tsc` against an API-only change, so it only works paired with the shared verifier or model-side verification.

Model-side verification is the most speculative piece and the evidence is specific. Execution-free trajectories "contain 40% fewer tokens" and span 10–30 turns versus 20–60 for execution-backed ones, with the accuracy gap concentrated on the hardest tasks ([arXiv 2604.01496](https://arxiv.org/pdf/2604.01496)). Execution-based and LLM-judge verifiers each plateau around 43% Best@K on SWE-bench Verified but combine to 51% ([arXiv 2504.07164](https://arxiv.org/pdf/2504.07164)). The cheap design is therefore a two-stage gate: a judge screens, execution confirms only on low confidence or disagreement. Practitioners who tried pure CI as the agent's verifier call it "miserable ergonomics for an agent" because of minutes-long batch loops ([Hacker News](https://news.ycombinator.com/item?id=49125061)), which is why the hybrid (cheap native affected-only checks locally, full matrix centrally before merge) is where the sources converge.

The requirements this imposes are concrete. The box needs KVM for the microVM path (or settles for runc plus swap, with gVisor costing 6–13× density for memory-heavy pods per Google's rows), fast local NVMe for swap and snapshots, and a single filesystem for the dependency store. The repo needs a lockfile and pnpm or Yarn PnP, no postinstall that writes into the tree, path-addressable tasks so "affected" is computable, deterministic tests (flakes poison speculation), and a tsconfig layout that lets one program serve a worktree. The agent harness needs to tolerate restores where the filesystem persists but processes do not, which Claude Code's cloud already enforces ("The cache stores files only, not running processes") ([Claude Code cloud environments](https://code.claude.com/docs/en/cloud-environments)).

## A redesign overturns five accepted ADRs, starting with "never snapshot a host"

The notes separate Manor's hard commitments (accepted ADR decisions) from incidental constants, and the density redesign collides with the former in specific places ([manor_constraints.md](../research_notes/Hundreds%20of%20agents%20on%20tiny%20boxes/manor_constraints.md)). The sharpest collision is **ADR-229 D5, "Never snapshot a host that has run Manor,"** with one identity per instance and secrets from environment rather than volume ([adr-229](../docs/decisions/adr-229-hosts-we-start/index.md)). Snapshot/restore is the single technique every vendor uses to reach density, so the redesign must redefine the unit being snapshotted: a sandbox that holds no Manor identity, no relay keys and no `~/.manor/remote/server/` state can be snapshotted freely, while the one host server per node keeps D5 intact. That is a workable reinterpretation, but it is a new decision, not a footnote.

| Commitment | Where | What the redesign needs | Verdict |
|---|---|---|---|
| One pod per project; pod per workspace stays out | [ADR-235](../docs/decisions/adr-235-pod-per-project/index.md) | Many projects per node sharing one server, or one sandbox per agent | Overturn |
| Never snapshot a host that has run Manor; one identity per instance | [ADR-229 D5/D6](../docs/decisions/adr-229-hosts-we-start/index.md) | Snapshot/restore of agent sandboxes | Overturn or narrow to "never snapshot the server, snapshot sandboxes" |
| Agents are never resumed automatically ("could repeat side effects") | [ADR-229 scope](../docs/decisions/adr-229-hosts-we-start/index.md) | Suspend between turns and restore on demand | Overturn or distinguish restore (same process state) from re-run |
| A recipe and a host are one-to-one; no per-workspace recipes | [ADR-229 D2](../docs/decisions/adr-229-hosts-we-start/index.md) | N sandboxes per recipe | Overturn |

| No Manor cloud backend holding credentials | [ADR-225 D8](../docs/decisions/adr-225-host-server/index.md) | Managed Agents puts the brain at Anthropic, not Manor; wake-from-phone stays impossible | Keep; it constrains but does not block |
| Credentials stay on the laptop; per-profile Secret is the one exception | [ADR-235 D9](../docs/decisions/adr-235-pod-per-project/index.md) | A thin worker needs a worker token or API key inside the sandbox | Tension; D9's Secret path may suffice |

The incidental constraints are easier and are already drifting: the `SIZES` presets have been changed once by commit, the 20 Gi PVC and 60-minute idle default are constants, the interactive `claude --dangerously-skip-permissions` TUI in a PTY, the forked Node subprocess per PTY with its 500 ms `pgrep` poll, the `sh`+`node` spawn per hook event, `requires_input` counting as busy, and idle stop depending on an awake laptop are all code, not decisions ([manor_constraints.md](../research_notes/Hundreds%20of%20agents%20on%20tiny%20boxes/manor_constraints.md)). The notes also observe that nothing architectural requires the TUI: the server already launches with no viewer, status already comes from hooks and transcripts rather than screen scraping, and resume is already a stored session id, so a headless runner needs a replacement for the PTY as the unit of layout (panes, scrollback, the phone's terminal view) but not for status tracking. The ADR-235 D10 baked host package, recorded as "Not yet run for real," is the existing seam for moving code into a shared read-only layer ([adr-235](../docs/decisions/adr-235-pod-per-project/index.md)).

## Compute is 1–15% of an agent-hour; "near zero" comes from tokens and borrowed hardware

Anthropic's own worked example for Managed Agents prices a one-hour Opus coding session at about **$0.705, of which the $0.08 runtime fee is ~11%**; idle time "waiting for your next message or a tool confirmation" does not count toward runtime ([Claude Platform pricing](https://platform.claude.com/docs/en/about-claude/pricing); [Finout](https://www.finout.io/blog/anthropic-just-launched-managed-agents.-lets-talk-about-how-were-going-to-pay-for-this)). A 2 vCPU / 4 GiB sandbox on E2B or Daytona costs about **$0.17 per wall-clock hour** at $0.000014/vCPU-s and $0.0000045/GiB-s ([E2B pricing](https://e2b.dev/pricing); [Daytona pricing](https://www.daytona.io/pricing)); Fly measured a Claude Code sandbox at 30% of 2 vCPU and 1.5 GB average and priced **100 agents for one hour at $5.93 on Sprites**, versus $16.56 on E2B/Daytona and $23.79 on Modal ([Fly.io](https://fly.io/learn/claude-code-sandbox-cost/)). Manor's own path is cheaper still: the Contabo Cloud VPS 12 from the earlier report (12 vCPU, 48 GB, $25–31/mo) is about **$0.04 per hour for the whole box**, which at 300 parked agents is roughly $0.00014 per agent-hour ([Budget VPS hosts for k3s](Budget%20VPS%20hosts%20for%20k3s.md)). On the token side, Opus 4.x is $5/$25 per MTok with cache reads at $0.50, Sonnet 5.5 is $2/$10, Haiku 5.5 is $0.10/$0.50 for prompts under 100K, and Fable 5.1 is $10/$50 with cache reads at $0.25; the Batch API takes 50% off, and the 4.7+ tokenizer produces ~30% more tokens for the same text ([Claude Platform pricing](https://platform.claude.com/docs/en/about-claude/pricing)). A realistic Claude Code hour of 100 turns re-reading a 100K cached context costs about **$5 in Opus cache reads alone** before output tokens ([reshaped_dev_loop.md](../research_notes/Hundreds%20of%20agents%20on%20tiny%20boxes/reshaped_dev_loop.md)), so compute is 1–15% of an agent-hour on rented sandboxes and well under 1% on an owned VPS.

Three facts follow. First, **"near zero" compute is already shipping**: Claude Code cloud sessions count "toward your plan's usage limits … and there's no separate charge for the cloud VM" on a 4 vCPU / 16 GB Ubuntu VM that pauses after a few minutes idle ([Claude Code docs](https://code.claude.com/docs/en/claude-code-on-the-web); [cloud environments](https://code.claude.com/docs/en/cloud-environments)); Jules bills by task caps with no compute line ([Jules usage limits](https://jules.google/docs/usage-limits/)); Cursor cloud agents are "charged at API pricing for the selected model" ([Cursor docs](https://cursor.com/docs/background-agent)). Vendors absorb the sandbox because it is immaterial next to inference. Second, the only path to literally zero marginal compute is hardware the user already pays for: Claude Code Remote Control runs the session on the laptop with the phone as "a window into that local session," and Anthropic's own docs route "workloads beyond these limits" to Remote Control ([cloud environments](https://code.claude.com/docs/en/cloud-environments)); StackBlitz's WebContainers run Node in the browser tab with "No paying by the minute for cloud VMs," which is how bolt.new's marginal cost became "AI tokens rather than hosting" ([webcontainers.io](https://webcontainers.io/guides/introduction); [PostHog](https://newsletter.posthog.com/p/from-0-to-40m-arr-inside-the-tech)). For Manor, an Electron app already on the developer's machine, this reframes the whole question: the marginal cost of N agents is laptop RAM, and the fix is the same sharing (one checkout image, one store, one typechecker daemon) rather than billing. Third, where compute does leak money is wall-clock-billed sandboxes left running while a human thinks (95% of the time) and memory-dominated bills on active-CPU platforms; pause-on-idle is the fix, and Manor's current design has the opposite, since `requires_input` keeps a pod up all night.

The levers that actually move the bill are token-side, and they are also what the reshaped loop delivers. Routing screening to Haiku 5.5 and edits to Sonnet 5.5 is 10–50× cheaper than Opus or Fable per token; keeping per-repo system context stable makes cache reads hit at 0.025–0.1× base price; execution-free drafting cuts tokens ~40% by halving turns ([arXiv 2604.01496](https://arxiv.org/pdf/2604.01496)); the Batch API halves non-interactive passes, though it is unavailable for Managed Agents ([Claude Platform pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Agentless resolved SWE-bench Lite issues at **$0.34–0.70 each**, almost entirely LLM cost ([arXiv 2407.01489](https://arxiv.org/html/2407.01489v2)); CodeMonkeys spent ~$4.60 per task for 57.4% ([Stanford](https://scalingintelligence.stanford.edu/blogs/codemonkeys)). The honest conclusion is that "agents make code changes at next to zero cost" is achievable for the compute term and not for the token term: a thin worker on a parked microVM drives the box to pennies per hundred agent-hours, but a frontier model reading a 100K-token repo context every turn costs dollars per hour per agent, and the research found no inference-time ablation showing a frontier agent keeps its accuracy with the turns that execution removes.

## Conclusion

The question began as "which resource runs out first" and the answer reframes it: the scarce resource on the box is resident memory held by processes that spend 92% of their life waiting, and the scarce resource overall is tokens, by one to three orders of magnitude over compute. That inverts Manor's current design priorities. ADR-235's pod-per-project isolation, the per-pod toolchain and the interactive TUI in a PTY all optimize for a world where the box is the expensive part; the evidence says the box is a rounding error and the model is the bill, so the right architecture spends compute freely on sharing (one repo image, one dependency store, one warm typechecker) and spends effort on reducing turns, context and model tier. The two-stage path is clean: stage one (requests sized to idle RSS, node swap, oxlint, many projects per host) is a quarter's work that touches one ADR and gets to low hundreds of parked agents on the $30 Contabo box; stage two (thin worker, snapshot-paused sandboxes, verification as a service) is a different product that rewrites five ADRs and needs a KVM-capable host.

Two things should be measured before either stage: a real idle pod (supervise + daemon + server + zero agents), since the 80 MB figure covers only the server, and the actual ESLint peak inside a pod, since the repo's own number doubled between the two measurements in these notes. The deeper unknown is whether Claude Code's roadmap resolves this for Manor: the open requests for a pooled MCP broker, hibernating idle sessions and a CLI-sized footprint ([#88524](https://github.com/anthropics/claude-code/issues/88524); [#98420](https://github.com/anthropics/claude-code/issues/98420)) would each remove a multiplier Manor currently pays for, and Managed Agents' self-hosted worker is Anthropic already shipping the thin-executor half of the redesign. Manor's distinctive asset is the laptop it already runs on; the version of "hundreds of agents on the tiniest box" most consistent with its ADRs may be the developer's own machine as the box, with the remote host reduced to a parked, snapshot-restored verifier.
