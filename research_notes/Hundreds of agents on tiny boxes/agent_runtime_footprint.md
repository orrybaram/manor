# Resource anatomy of coding-agent runtimes and the lightest feasible alternatives (as of 2026-10-16)

Notes on where a coding-agent process's memory and CPU go, measured footprints of Claude Code and competing CLIs, MCP server overhead, thin-client/split architectures, idle-time ratios, and stateless-per-turn feasibility.

Conventions: "[Local]" marks measurements I ran on 2026-10-16 on the user's macOS arm64 dev box (Darwin 27.0, Node v24.13.0, Bun 1.3.10, Claude Code 2.1.301 native install). They have no URL; the command is given so they can be reproduced. "[Est.]" marks my estimates. Dates of third-party measurements are noted inline.

## Key Question 1: Baseline RSS of Node / Bun / Deno / Go / Rust; V8 isolate cost; effect of --max-old-space-size, --jitless, snapshots

### Takeaway
A do-nothing Node 24 process is ~39 MB RSS, Bun ~18–20 MB, Python ~13 MB, a C `sleep` ~1 MB; Go/Rust hello-world servers are single-digit MB. `--jitless` and `--max-old-space-size` do not reduce idle RSS at all (they bound growth / trade speed); startup snapshots halve Node start time (~40 ms → ~20 ms) but do not shrink resident memory. The runtime floor (~20–40 MB) is a rounding error against the 180–700 MB Claude Code sessions actually use, so the bulk of agent memory is application state and bundle, not the JS runtime.

### Cited Findings
- [Local] `node -e 'setTimeout(()=>{},1e4)'` idle RSS 39 MB; `node --jitless` 39 MB; `node --max-old-space-size=64` 39 MB; `bun -e ...` 20 MB; `python3 -c 'time.sleep'` 13 MB; `sleep` 1 MB (measured with `ps -o rss=` 1.5 s after spawn). Startup: `node -e 0` real 0.02 s; `bun -e 0` real 0.01 s. — [Local measurement, 2026-10-16; no URL]
- [Local] `bun build --compile` of a one-line script produced a 58.1 MB single-file executable whose idle RSS was 18 MB. — [Local measurement, Bun 1.3.10, 2026-10-16; no URL]
- Secondary 2026 runtime-comparison posts report idle process memory of ~18 MB Bun, ~30 MB Deno, ~40 MB Node. These appear to be one unverified test repeated across posts. — [dev.to / Pockit Tools](https://dev.to/pockit_tools/deno-2-vs-nodejs-vs-bun-in-2026-the-complete-javascript-runtime-comparison-1elm)
- Conflicting data on Bun memory: DreamHost's 2023 tests found Bun used noticeably more memory than Node; newer 2026 data it cites reports Bun using 25–40% less for API servers, while a production migration found the two within ~15% under sustained load. — [DreamHost](https://www.dreamhost.com/blog/bun-vs-node/)
- "A basic Node Lambda running no real code consumes 35 MB of memory." With a shared V8 runtime across isolates "that drops to around 3 MB." "Isolates start in 5 milliseconds" and "around a hundred times faster" than a Node process (vendor claim, Nov 2018). — [Cloudflare blog](https://blog.cloudflare.com/cloud-computing-without-containers/)
- V8 `--jitless` (V8 v7.4, March 2019): "disables all runtime allocation of executable memory"; cost: Speedometer 2.0 ~40% slower, Web Tooling Benchmark 80% regression; memory benefit: a median 1.7% decrease in V8 heap size on representative websites. — [v8.dev](https://v8.dev/blog/jitless)
- A blog claims `--jitless` cuts V8 isolate memory "up to 45%"; no methodology, promotional, treat as unconfirmed and contradicted by both V8's own 1.7% figure and the local 39 MB → 39 MB result. — [businesstechnavigator](https://businesstechnavigator.com/blog/nodejs-26-jitless-era-v8-overhead)
- V8 pointer compression (32-bit heap pointers) gave "~50% reduction in heap usage" on real Next.js SSR apps at +2.5% average latency (Node 25 builds, ~Feb 2026); requires a 4 GB heap cap per isolate and is not in official Node builds (shipped as Platformatic's `node-caged` image). — [Platformatic](https://blog.platformatic.dev/we-cut-nodejs-memory-in-half)
- Node startup profile: `./node -e 0` ≈ 23.3 ms elapsed; the ~1.45 MB isolate snapshot deserializes in ~5.9 ms, context in ~2.5 ms; snapshot init ≈ one third of startup. — [kvakil.me, May 2023](https://kvakil.me/posts/2023-05-11-nodejs-startup-series-externalizing-startup-strings.html)
- Node user-land startup snapshots (`--snapshot-blob`, experimental since v18.8) reported to cut Node startup from ~40 ms to ~20 ms on a MacBook (talk recap). — [GitNation](https://gitnation.com/contents/boosting-nodejs-startup-performance-with-startup-snapshots); [LogRocket](https://blog.logrocket.com/snapshot-flags-node-js-v18-8)
- Electron embedding Node's snapshot: time to first main-process JS 123 ms → 74 ms (~40%), spawn-to-ready 198 ms → 149 ms, at +4.6 MB binary size. — [Electron PR 51703](https://releases.electronjs.org/pr/51703)
- Go vs Rust hello-world HTTP servers in Docker: Go ~4 MB, Rust ~7 MB RSS; Python ~13 MB (anecdotal forum post). — [linux.org.ru](https://www.linux.org.ru/forum/development/13094977)
- Go hello-world binary ~2.0 MB (Go 1.10 era). — [Go commit](https://lab.nexedi.cn/kirr/go/-/commit/0cdf2ec81a07e8d8303e24aab49df137b355fa3b); Rust stripped hello ~160 KB once jemalloc removed (2017). — [nim IRC log](https://irclogs.nim-lang.org/20-04-2017.html)
- Anthropic's Go `ant` CLI (used as the self-hosted sandbox worker) release `ant_1.42.0_linux_amd64.tar.gz` is 12 MB compressed (published 2026-10-15). — [anthropics/anthropic-cli releases](https://github.com/anthropics/anthropic-cli/releases)
- Daytona release binaries `daytona-linux-amd64` 18 MB / `daytona-linux-arm64` 17 MB (v0.190.0). — [daytonaio/daytona releases](https://github.com/daytonaio/daytona/releases)
- OpenAI Codex CLI (Rust) release `rust-v0.163.0` (2026-10-15): `codex-x86_64-unknown-linux-musl.tar.gz` 107 MB, `codex-aarch64-apple-darwin.tar.gz` 94 MB. — [openai/codex releases](https://github.com/openai/codex/releases)
- [Local] Claude Code 2.1.301 native binary at `~/.local/share/claude/versions/2.1.301` is a 238.9 MB Mach-O arm64 executable; the npm platform package `@anthropic-ai/claude-code-darwin-arm64@2.1.301` reports `dist.unpackedSize` 250,542,417 bytes. — [Local + `npm view`, 2026-10-16]

### Inferences
- The JS runtime floor (Node ~39 MB, Bun ~18 MB) accounts for at most ~10–20% of an idle Claude Code session (181–350 MB). The remaining ~150–300 MB is bundle code, loaded modules, tool/MCP schemas, and transcript held in the heap (see Q2).
- `--max-old-space-size` is a ceiling, not a diet: it only changes when GC runs or when the process OOMs. It is useless for lowering idle RSS and harmful when the leak is off-heap (Q2, #67433).
- Pointer compression is the only V8-level knob with a large measured win (~50% heap), but it is unavailable in stock Node and irrelevant to a Bun-compiled binary.
- [Est.] A Go or Rust executor binary can be 2–20 MB on disk and 4–10 MB RSS idle, i.e. 20–50x smaller than a Claude Code session.

### Gaps
- No rigorous, same-machine hello-world RSS table for Node 20/22 vs Bun vs Deno vs Go vs Rust exists in the sources found; the Deno figure (~30 MB) is from a secondary blog only and Deno was not installed locally to measure.
- Per-isolate V8 memory cost in MB (beyond Cloudflare's "3 MB shared runtime" claim) was not found; V8's own blog posts on memory were not fetched.
- No measurement of RSS for `node --snapshot-blob`, `deno compile`, or `bun build --compile` on a real agent bundle (only the trivial 58 MB / 18 MB hello-world above).

## Key Question 2: Claude Code CLI's footprint and competing agent CLIs (Codex, Gemini CLI, Aider, OpenCode, Goose, Amp, Cursor CLI)

### Takeaway
Claude Code is a ~239–250 MB Bun-compiled native binary (not Node) whose idle session RSS is reported at ~180 MB fresh, 250–350 MB after a resume, and 500–700 MB after long sessions, growing with transcript and MCP schema size; multiple off-heap leak regressions (400–500 MB/min idle) have been filed in 2026, and a background daemon with pre-warmed "bg-spare" workers adds hidden resident processes. Codex CLI is Rust but its release tarballs are ~100 MB and no idle-RSS measurement was found; Gemini CLI (Node) has OOM-at-init and orphaned-process reports; OpenCode has anecdotal ~1 GB TUI reports; no data at all for Aider, Goose, Amp, or Cursor CLI.

### Inferences
- Where Claude Code's ~180 MB fresh baseline goes [Est.]: ~18–20 MB Bun runtime (local hello-world), the remainder is the ~240 MB bundle being parsed/loaded plus React/Ink TUI state, tool and MCP schema JSON, settings, and plugin/skill indexing. The growth from 181 → 320 MB on `claude -c` (#98420) is transcript rehydration; the growth to 500–700 MB over hours is transcript + rendered-message retention + off-heap buffers.
- Because the leak class most often reported is anonymous/off-heap (#67433, #28763), V8 heap caps cannot contain it; process-level limits (cgroup `memory.max`) are the only reliable ceiling.
- Multi-session hosts carry hidden overhead beyond N × session RSS: the background daemon's spare worker pairs (#99931, ~200 MB per pair) and one MCP child per session (local: 54–64 MB each).
- The AgentCgroup "~185 MB baseline" in a headless container matches #98420's 181 MB fresh TUI start, so the TUI itself is not the dominant cost; the bundle and agent state are.
- Codex CLI being Rust does not make it small on disk (~100 MB); without measurements its idle RSS cannot be assumed to be dramatically lower.

### Gaps
- No measured idle RSS or startup time for Codex CLI (bare `codex` binary), Gemini CLI, Aider, Goose, Amp, or Cursor CLI was found. GitHub issue searches for Codex returned only desktop-app issues.
- No Anthropic statement breaking down Claude Code memory by component, and no maintainer response on the footprint feature request (#98420 has 0 comments).
- The 100 MB binary / Bun 1.4.0 claim comes from an unverifiable host and conflicts with the local 239 MB measurement.
- No measurement of a true Claude Code session cold start (launch → prompt ready) was found beyond user bug reports (0.6 s to 46 s depending on plugins/config).

## Key Question 3: What MCP servers cost per agent; evidence of MCP memory bloat

### Takeaway
Each stdio MCP server is typically its own Node process at roughly 50–75 MB RSS (locally 54–64 MB), spawned per agent session with no sharing, so cost scales as sessions × servers; the dominant evidence of bloat is multiplication and orphaning (dozens to hundreds of node processes, 4.5–10 GB idle), plus each session also holding every server's tool schema in its own heap.

### Cited Findings
- [Local] Each of 5 Claude Code sessions had one child `node mcp-webview-server.js` (Manor's MCP server) at 54, 54, 56, 58, 64 MB RSS. — [Local, 2026-10-16]
- Claude Code on Windows with many plugins + 1M context: ~50–75 MB each across 17 MCP processes. — [claudeissues 51476](https://claudeissues.com/issue/51476-high-ram-consumption-from-node-mcp-subprocesses-on-windows-many-plugins-1m-conte)
- Claude Code: "Multiple concurrent sessions multiply MCP server processes without memory limits" — up to N×M node processes (N sessions, M servers), no documented per-subprocess heap cap; user workaround `NODE_OPTIONS=--max-old-space-size=<N>`. — [claudeissues 45880](https://claudeissues.com/issue/45880-bug-multiple-concurrent-sessions-multiply-mcp-server-processes-without-memory-li)
- Gemini Code Assist / IDE: "72 node.js processes consuming ~4.5 GB at idle from 4 workspaces and 9 servers" (≈62 MB per process); MCP servers spawned per workspace. — [Google AI forum](https://discuss.ai.google.dev/t/bug-mcp-servers-spawn-per-workspace-causes-process-explosion-and-10-gb-idle-ram/129054); orphaned MCP server processes accumulate after conversations end, exhausting memory. — [Google AI forum](https://discuss.ai.google.dev/t/bug-all-mcp-server-processes-are-orphaned-after-conversation-ends-accumulate-indefinitely-causing-system-memory-exhaustion/139866)
- Codex desktop (Windows, Oct 2026): "One stdio MCP process set per thread; 13 sets / 353 processes / ~9.6 GiB under a single app-server, reclamation lags creation" (≈27 MB per process average, ~740 MB per thread's set). — [openai/codex #53285](https://github.com/openai/codex/issues/53285)
- Codex: app-server "leaks MCP process stacks for subagents, causing linear memory growth on Linux". — [openai/codex #25015](https://github.com/openai/codex/issues/25015)
- Claude Code #88524: each session holds "the complete tool/MCP-schema payload in its V8 heap"; with ~15 servers of 60–100 tools each, RAM "scales linearly with (open chats × enabled servers)"; asks for "a pooled broker daemon" so MCP connections and schemas are shared. — [#88524](https://github.com/anthropics/claude-code/issues/88524)
- A guide reports stateless npm MCP servers at "roughly 2–3 MB per process" and a server with a DB connection pool at ~65 MB. The 2–3 MB figure is implausible for a Node process (Node floor is ~35–39 MB per Q1) and is likely a heap-only or mis-stated number; treat with caution. — [fast.io](https://fast.io/resources/mcp-server-memory-management/)
- A Node MCP server stress-test doc reportedly measured ~143 MB RSS at start with a ~51 MB bump on first request; the page content could not be loaded to verify. — [glama.ai mirror (unverified)](https://glama.ai/mcp/servers/@pshempel/mcp-time-server-node/blob/259726a6beceef3a44dde4dc154f65fa20dac3bb/docs/verified-behaviors/python-stress-test-research.md)

### Inferences
- Rule of thumb [Est.]: budget ~60 MB RSS per stdio Node MCP server per agent session, plus a few MB of schema JSON inside the agent's own heap per server. Ten sessions × five servers ≈ 3 GB before any agent work happens.
- The fix pattern every tracker converges on is the same: one shared MCP broker per host (or remote/HTTP MCP servers) so processes and schemas are shared across sessions. No agent CLI surveyed ships this today (Claude Code #88524 is open).
- Remote (HTTP/SSE) MCP servers move the process cost off the agent host entirely; only the schema stays in the agent heap. #67433 suggests many remote MCP servers can still contribute to off-heap growth via keepalive/poll buffers, but that is the reporter's hypothesis, not a confirmed cause.

### Gaps
- No controlled benchmark of MCP server RSS by implementation language (Node vs Python vs Go/Rust) was found; the figures above are all incidental to bug reports.
- No measurement of how much schema per server (KB/MB) each agent session retains in-heap.

## Key Question 4: Thin-client / split architectures and the minimal in-sandbox executor

### Takeaway
Anthropic Managed Agents already implements the split: Claude's agent loop runs on Anthropic's control plane and a worker inside the sandbox only executes bash/file tools and posts results back; the reference worker is the Go `ant` CLI (12 MB compressed), needing only `/bin/bash` and outbound HTTPS, and can run one-shot per session in a fresh container. The Claude Agent SDK is not thin (it runs the full Claude Code binary). Sandbox vendors (E2B, Daytona, Sprites, Modal, Vercel, Cloudflare) each run a small Go-style daemon or agent API inside the VM, and several pause idle sandboxes to $0 compute with sub-second to few-second restores. A <20 MB executor (shell + git + HTTP stub) is clearly feasible: the executor binaries that exist are 2–18 MB.

### Cited Findings
Anthropic
- Agent SDK is "A library that runs the Claude Code binary, with Claude Code's capabilities"; Managed Agents is "A hosted agent harness that runs the agent loop, with sessions in an Anthropic-managed cloud sandbox or a self-hosted sandbox". Other languages "run the CLI as a subprocess with the `-p` flag". — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- Managed Agents self-hosted sandboxes (beta `managed-agents-2026-04-01`): "A `self_hosted` environment acts as a work queue. You run an environment worker ... Your worker claims the work item and downloads the agent's skills and the session's memory stores. Claude runs on Anthropic's side and requests tool calls. Your worker runs each call locally and posts the result back." Prerequisites: "A Linux host: The host needs `/bin/bash` at that exact path. The worker needs only outbound HTTPS." Worker: `ant beta:worker poll --workdir /workspace`. Pre-built workers in `ant` CLI and Python/TypeScript/Go SDKs. "If no worker is connected, the session stays queued rather than failing." — [Self-hosted sandboxes](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes)

### Inferences
- The Managed Agents self-hosted worker is the canonical "tool executor": Go binary, ~12 MB compressed (likely ~30–40 MB uncompressed [Est.]), needs bash and HTTPS only. Its idle RSS was not measured here but Go daemons of this class run at single-digit to low-tens of MB [Est., from Q1 Go figures].
- A purpose-built executor (static Go/Rust binary wrapping `bash`, `git`, file ops, and one HTTPS long-poll) at <20 MB on disk and <15 MB RSS is consistent with every data point above (Go hello 2 MB / 4 MB RSS; Daytona 18 MB; ant 12 MB). The agent loop, model calls, transcript, and MCP schemas live elsewhere, which is exactly the memory that dominates Claude Code (Q2).
- The Agent SDK does not help: every SDK agent spawns a full ~250 MB Claude Code binary, so its footprint equals a CLI session.
- "Hundreds of agents on one small box" is therefore an architecture choice: either (a) self-hosted Managed Agents workers (brain at Anthropic, ~tens of MB per sandbox), or (b) a custom loop calling the Claude API with a tiny executor per repo; running hundreds of Claude Code CLI processes is bounded by ~185 MB × N baseline plus leaks plus MCP children.

### Gaps
- No published binary size or RSS for E2B's `envd`, Daytona's in-sandbox daemon (the 18 MB release asset is the CLI/server binary, not confirmed as the in-sandbox component), Vercel's or Cloudflare's agent, or Anthropic's cloud-sandbox agent.
- No official resource specs for Anthropic's own hosted Managed Agents sandbox or Claude Code on the web (the 4 CPU / 8 GB figure is third-party).
- Whether Codex cloud runs the full Codex CLI inside the container or a thin executor is not documented in the sources found.
- Idle RSS of `ant beta:worker poll` was not measured (I did not execute the downloaded binary).

## Key Question 5: Share of agent time spent waiting on the model vs executing tools vs idle

### Takeaway
Within an active turn, LLM time is usually the larger share (40–45% of end-to-end in AgentCgroup; 71–98% in another study; tool time 13–39% depending on benchmark and harness), but at the session level human/idle gaps dominate: TraceLab's real Claude Code and Codex traces show an average 46.7 min gap between user requests (median 1.4 min), ~13 s per LLM generation and ~18 s per tool call, with 61% of tool calls under 1 s. The CPU average while a coding agent is active is only 7.6–13.2% of one core, so a process is effectively idle most of its life.

### Cited Findings
- AgentCgroup (Claude Code in Podman, 144 SWE-rebench tasks, Haiku 4.5 and GLM-4.7-Flash): latency = LLM reasoning 40–45%, tool execution 13–24%, initialization (container + agent) 31–48%; "OS-level execution ... accounts for 55-60% of end-to-end task latency"; tool share of active time 19.8% (Haiku) / 34.9% (GLM); CPU average 13.2% / 7.6% of a core, peaks >175%; only 0.5% (GLM) / 8.2% (Haiku) of samples exceed 50% CPU; "memory, not CPU, is the concurrency bottleneck"; memory peak-to-average up to 15.4× (4060 MB peak vs 264 MB average on pydicom#2022), driven by test execution (P95 518 MB Haiku) and package installs (~233 MB); task mean 5.8 min (Haiku) / 10.8 min (GLM). — [arXiv 2602.09345](https://arxiv.org/html/2602.09345v3)
- "Agentic AI Workload Characteristics": LLM inference 71–98% of total runtime, tools 2–29%; SWE-bench Pro and Terminal Bench ≈17–18% tool time. — [arXiv 2605.26297](https://arxiv.org/pdf/2605.26297)
- "Not All AI Agents Are Equal": coding "dominated by LLM API time"; local Bash execution 39% on average across three coding benchmarks; "faster LLM responses or more CPU cores do not always accelerate agents". — [arXiv 2609.19947](https://arxiv.org/pdf/2609.19947)
- Aries framework: tool execution 13% to 48% of total latency across datasets/harnesses, high end on Terminal-Bench 2. — [arXiv 2607.29069](https://arxiv.org/pdf/2607.29069)
- TraceLab (UW SyFI, 2026-06-25; ~4,300 real Claude Code and Codex sessions, 55B tokens, 433K tool calls): LLM generation averages ~13 s, tool call ~18 s, user gap between requests averages 46.7 min (median ~1.4 min); request end-to-end median ~38 s, mean ~4 min, p99 ~44 min; 8.8 steps and 10.8 tool calls per request; 88% of LLM rounds respond to a tool result; calls <1 s ≈61% of calls but ~1% of tool time; calls >1 min ≈4% of calls but ~85% of tool time; Bash latency spans >4 orders of magnitude. — [TraceLab blog](https://syfi.cs.washington.edu/blog/2026-06-25-tracelab/)
- TraceLab session-level breakdown (search summary of the interactive page): human thinking 92.3% of session wall-clock, LLM generation 3.3%, tool execution 4.8%; within requests tool execution 59.8% vs generation 41.0% (figures as reported by search; not independently re-read). — [TraceLab session timing](https://tracelab.cs.washington.edu/exp/session/session_timing_distribution/)
- GitHub Copilot production traces (13.5M sessions) reported as "87% agent, 13% human" time share (secondary blog). — [codex.danielvaughan.com](https://codex.danielvaughan.com/2026/09/01/agentic-coding-wild-github-copilot-production-traces-kv-cache-codex-cli/)

### Inferences
- For interactive sessions, >90% of wall-clock is waiting on a human, and within an active turn roughly half is waiting on the model: the process needs CPU for well under 10% of its life, matching the user's own 0.01–0.08 idle cores and 0.26 cores active.
- The tool-time tail matters for suspension design: 85% of tool time is in the 4% of calls that exceed a minute (test suites, installs), which also produce the memory spikes (peak/avg 15×). A design that suspends between turns must still allow bursts of CPU and RAM inside a turn, so per-agent cgroup limits should be set on the burst, not the idle average, or tests will OOM.
- The sources disagree on tool share (13% to 48%) because they measure different harnesses and denominators (with or without container init); the consistent finding is that CPU is rarely the bottleneck and memory is.

### Gaps
- No study reports the fraction of time an interactive Claude Code session's process is truly idle at the prompt in production (TraceLab's 92.3% is the closest, from the authors' own usage).
- No measurement of CPU during the "waiting on API stream" state specifically (streaming JSON parsing and TUI re-rendering) versus true prompt-idle.

## Key Question 6: Stateless-between-turns agents; cold-start cost of re-spawning per turn

### Takeaway
Claude Code's conversation state already lives entirely in the JSONL transcript (`claude --resume` reconstructs a session), and Anthropic's Managed Agents treats the sandbox worker as disposable per session, so a stateless per-turn executor is architecturally established. The cost is cold start: a bare Node or Bun process starts in 10–25 ms, but a Claude Code session cold start is reported at ~0.6 s minimum and typically several seconds (plugins, settings, MCP connections, Bedrock probing), and a resumed long session rehydrates to ~320 MB within 34 s; microVM/snapshot restores are 25 ms–3 s depending on vendor.

### Cited Findings
- "Its whole state is in its transcript, and `claude --resume <id>` brings it back"; proposes exiting cleanly on SIGTERM with the transcript flushed and printing the resume command. — [anthropics/claude-code #102115](https://github.com/anthropics/claude-code/issues/102115)
- `claude -c` (continue) measured at 320 MB RSS 34 s after resume vs 181 MB fresh (v2.1.285). — [#98420](https://github.com/anthropics/claude-code/issues/98420)
- Claude Code idle sessions retain full transcript + schemas in heap indefinitely; "Idle sessions should be able to release or hibernate memory" is an open request. — [#88524](https://github.com/anthropics/claude-code/issues/88524)
- Managed Agents sandbox-per-session: the container "reads session details from environment variables, handles that session, and exits"; webhook-triggered workers avoid an idle poller; queued sessions wait for a worker rather than failing. — [Deploy self-hosted workers](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes-workers); [Self-hosted sandboxes](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes)
- Cloudflare's Managed Agents template "saves the sandbox state while the session sleeps". — [Cloudflare docs](https://developers.cloudflare.com/sandbox/claude-managed-agents/)
- Runtime cold start: `node -e 0` ≈ 23.3 ms (perf stat, 2023). — [kvakil.me](https://kvakil.me/posts/2023-05-11-nodejs-startup-series-externalizing-startup-strings.html); [Local] `node -e 0` 0.02 s, `bun -e 0` 0.01 s (2026-10-16). Snapshots cut Node start ~40 → ~20 ms. — [GitNation](https://gitnation.com/contents/boosting-nodejs-startup-performance-with-startup-snapshots)
- Claude Code cold start reports: `--version` ~600 ms. — [claudeissues 8164](https://claudeissues.com/issue/8164-bug-claude-cli-is-slow-to-start); 4.4 s with empty plugin cache. — [15090](https://claudeissues.com/issue/15090-bug-plugin-cache-causes-10x-startup-delay-inverted-cache-behavior); +4.3 s Bedrock probing. — [49138](https://claudeissues.com/issue/49138-bug-showsetupscreens-bedrock-fallback-tier-probing-adds-4-3s-to-startup); "Local MCP servers fail with 'Not ready after 60 seconds'" (MCP connect is part of startup). — [#92758](https://github.com/anthropics/claude-code/issues/92758)
- Claude Code's background daemon pre-spawns `bg-spare` workers to make spawning fast, at the cost of resident pairs (~200 MB each, 7–8 pairs ≈ 1.6 GB). — [#99931](https://github.com/anthropics/claude-code/issues/99931)
- AgentCgroup: initialization (container + agent) is 31–48% of task latency; retries can leave up to 502 MB unreleased. — [arXiv 2602.09345](https://arxiv.org/html/2602.09345v3)
- Sandbox restore latencies (vendor claims unless noted): E2B ~150 ms; Blaxel ~25 ms from standby; Fly Sprites 100–500 ms warm, 1–2 s create; Cloudflare 1–3 s; Upstash Box ~0.4 s (measured by Upstash); Modal has no pause, memory snapshots alpha. — [Upstash comparison, 2026-09-17](https://upstash.com/blog/ai-agent-sandbox-providers-compared-2026); Sprites checkpoints "~300ms", last five retained (secondary). — [letsdatascience](https://letsdatascience.com/news/flyio-launches-spritesdev-sandbox-environments-with-checkpoi-61b41ce7)
- GKE snapshot-suspend of idle agents saved ~40% compute typical, up to 90%. — [ZenML LLMOps DB](https://www.zenml.io/llmops-database/high-performance-agent-infrastructure-with-gke-sandboxing-and-snapshots)
- OS-level alternative to re-spawn: raise `oom_score_adj` to 1000 while idle (allowed without privilege; verified on Linux 7.0 in the report) so idle sessions are evicted first and resumed from transcript. — [#102115](https://github.com/anthropics/claude-code/issues/102115)

### Inferences
- Re-spawning Claude Code per turn is feasible but costs seconds, not milliseconds: runtime start (~20 ms) is negligible; the bundle load, settings/plugin scan, MCP server handshakes (each a fresh ~60 MB Node child), and transcript rehydration dominate. For a 46.7-min average inter-turn gap (Q5) that overhead is acceptable; for the 1.4-min median gap it is noticeable but still a small fraction.
- A thin executor + remote loop (Q4) makes per-turn statelessness nearly free: the Go worker starts in tens of ms, holds no transcript, and the "state" is the repo on disk plus the transcript on the control plane.
- The cheapest intermediate on a single box, needing no architecture change: keep sessions resident but (a) suspend with SIGSTOP or a cgroup freezer between turns (CPU → 0, RAM unchanged), (b) rely on swap/zram for cold heaps (macOS already compresses idle heaps per #88524, at a 58% sys-CPU thrash cost when oversubscribed), or (c) kill idle sessions and `--resume` on demand, accepting a multi-second resume. Only (c) reduces RSS.
- [Est.] With memory-snapshot-capable microVMs (E2B, Blaxel, GKE), a parked agent costs disk only and restores in 25–150 ms, which is the closest existing thing to "near-zero resident memory between turns" for a full Claude Code process.

### Gaps
- No measurement of a Claude Code `--resume` cold start to first token or of `claude -p` end-to-end startup overhead was found or made (not run locally to avoid API spend and auth prompts).
- No data on CRIU/checkpoint-restore of a bare Claude Code process outside microVM vendors.
- No documentation on whether Claude Code's bg-spare daemon can be disabled or capped (#99931 requests a setting; none found in docs).
- Whether Anthropic's own hosted Managed Agents sandboxes snapshot/park between turns is not documented.
